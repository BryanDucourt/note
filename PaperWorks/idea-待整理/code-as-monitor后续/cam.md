# **结论先行**

截至 **2026 年 7 月 30 日**，CaM 作为 CVPR 2025 工作，其核心判断仍然成立：把任务语义编译成可执行约束监控代码，比持续调用 VLM 做视觉问答更适合在线监控。 

但在 CaM 之后，这个方向发展很快，若只是进行以下改动，已经很难形成足够强的新工作：

- CaM + 一个学习式故障分类器；
- CaM + VLA 隐层特征；
- CaM + 失败后重规划或重试；
- CaM + 任务图和预定义恢复分支；
- CaM + LTL/STL 约束；
- CaM + 世界模型预测一个失败分数；
- CaM + 普通实时 DAG 调度器。

目前最有价值、同时与 CaM 原始缺陷直接对应的两个方向是：

1. **可验证且不确定性感知的 Code-as-Monitor**：解决“谁来保证生成的监控代码本身正确”；
2. **风险驱动的实时监控运行时**：解决“计算资源受限或受到干扰时，关键约束能否按时被监控”。

结合你已有的实时调度、sched_ext、ROS2 和工作流框架积累，第二条与已有研究路径最容易衔接；从机器人论文的完整性和直接性看，第一条更容易形成一篇独立、故事清晰的工作。

# **一、CaM 之后的最新相关文献版图**

下面优先列与 CaM 的“运行时故障监控、语义约束、主动预警和恢复”直接相关的工作。2026 年部分论文仍是 arXiv 预印本，需要与正式发表工作区别对待。

## **1. 运行时故障检测与不确定性估计**

|**工作**|**状态**|**核心方法**|**对 CaM 的影响**|
|---|---|---|---|
|**Sentinel: Unpacking Failure Modes of Generative Policies**|CoRL 2024，PMLR 2025|将故障分成动作时序不一致和任务进展停滞，分别用统计检测器和低频 VLM 检测；组合检测器比单独使用任一检测器多识别约 18% 的故障。|说明单一几何约束监控未必足够，不同故障应由不同专用检测器处理。|
|**FAIL-Detect**|RSS 2025|只使用成功数据，把故障检测转化为顺序 OOD 检测，并用 conformal prediction 提供统计校准。|直接暴露 CaM 的不足：CaM 的阈值主要由人工或 VLM 给出，没有统计覆盖保证。|
|**SAFE**|NeurIPS 2025|从 OpenVLA、π₀、π₀-FAST 等 VLA 的内部特征中学习跨任务故障表示，并用 functional conformal prediction 决定时变阈值，可泛化到未见任务。|“CaM + VLA 隐层特征检测器”已经不是新的方向。|
|**I-FailSense**|arXiv，v3 更新于 2026 年 2 月|重点检测“语义错位”，即机器人动作本身合理，但与语言指令不一致；通过 VLM 内部层上的轻量 FS heads 进行判断。|CaM 的几何约束容易覆盖掉落、倾斜等物理错误，但不一定能覆盖“拿错对象、漏掉步骤、误解任务”等语义错误。|
|**ReconVLA**|arXiv，2026 年 4 月|对 VLA 动作 token 应用 conformal prediction，并通过机器人状态空间 OOD 检测进行主动预警。|简单地为 CaM 加置信度或 conformal threshold 已经不足，需要做到**谓词级、可解释的置信校准**。|
|**Foresight**|arXiv，2026 年 6 月|使用 action-conditioned world model 的潜变量监控长时程任务，只需最终成功/失败标签，并使用 functional conformal prediction 校准检测阈值。|“CaM + 世界模型故障分数”已经较拥挤；必须突出显式约束、反事实解释或控制干预。|
|**Uncertainty Quantification for Flow-Based VLA / SAVE**|arXiv，2026 年 6 月|通过 flow matching 速度场分歧估计认知不确定性，用于故障检测和主动微调。|对基于 π₀ 一类 flow-based VLA 的不确定性估计已经出现专门方法。|

这一组工作意味着：**“提高故障检测准确率”本身已经不够构成创新**。新的工作必须回答 CaM 和纯学习式检测器都没有解决的问题，例如：

- 监控逻辑是否语义正确；
- 置信度对应的是哪个约束、哪个对象和哪种错误；
- 在资源不足时，哪些监控必须优先执行；
- 检测结果能否提供统计或时序保证。

## **2. 故障解释、恢复与自纠正**

|**工作**|**状态**|**核心方法**|**对 CaM 的影响**|
|---|---|---|---|
|**FPC-VLA**|arXiv，2025|采用 VLA + 视觉语言监督器的双模型架构，监督器判断动作可行性并生成修正策略。|“外挂监督模型判断并纠正 VLA”已经被直接覆盖。|

|**Guardian / FailCoT**|arXiv，v3 更新于 2026 年 3 月|扰动成功轨迹生成跨环境失败，构建逐步失败推理数据，并训练多视角失败推理 VLM。|单纯扩大失败数据集或增加 CoT 推理也已较拥挤。|

|**CycleVLA**|arXiv，v2 更新于 **2026 年 7 月 28 日**|通过子任务回退和 minimum Bayes risk decoding 实现主动自纠正；真实机器人平均成功率达到 91%，并修正约 80% 的注入故障。|“检测后回退、重新执行、VLA 自纠正”已经不是空白。|
|**AgentChord**|RSS 2026|执行前把可能故障及恢复动作编译进有向任务图，运行时由低延迟监控器直接切换到预编译恢复分支，不再临时重新规划。|这是最需要警惕的撞题工作。**CaM + 工作流图 + 预定义恢复分支**这一条线已经被高度覆盖。|

特别是 AgentChord 已经明确批评 CaM 一类方法的恢复方式：生成的监控逻辑可能过于简单，而且检测后重新调用完整规划流程会引入较高延迟。它通过执行前构建恢复增强任务图来解决这一问题。 

因此，你现有的 workflow engine、retry/replan 和故障分支更适合作为**系统基础设施**，不能再直接作为论文主创新。除非进一步转向：

- 多机器人分布式约束；
- 部分可观测情况下的跨机器人一致性；
- 有界通信延迟；
- 共享资源冲突；
- 可证明的时序契约与恢复正确性。

# **二、CaM 真正留下了哪些可发表的问题**

CaM 自己在补充材料中已经暴露了几个关键缺口。

## **1. 监控代码“能运行”，不等于“监控逻辑正确”**

CaM 在每个子目标开始时使用当前状态做 white-box path coverage，检查各个 if-else 分支能否执行；出错则重新生成代码。但这种检查主要验证：

- 是否有语法或运行时错误；
- 分支是否能被执行；
- 当前输入下代码是否返回结果。

它不能保证：

- 使用了正确对象；
- 坐标系是否一致；
- 米和厘米是否混用；
- 平面法向量方向是否取反；
- 阈值是否符合当前物体和任务；
- “保持抓取”是否被错误实现成“距离足够近”；
- 当前状态恰好通过测试，但未来状态逻辑错误。

CaM 还明确说明，常见任务阈值来自人工知识库，未见任务阈值由 VLM 生成，而不同条件下阈值变化的影响尚未研究。 

这是目前最强的创新入口：

**CaM 把控制策略视为不可信对象，却默认生成的 monitor 基本可信；新工作可以把 monitor 本身也视为需要验证和校准的不可信程序。**

---

## **2. 监控结果是二值的，但感知输入具有不确定性**

CaM 最终输出：

```text
constraint_satisfied = True / False
```

但其输入来自：

- 分割；
- 深度；
- 多视角配准；
- 点云聚类；
- CoTracker 跟踪；
- 遮挡后的插值。

这些输入都不是确定值。现有 CaM 没有把感知误差传播到约束判定中，因此会出现：

- 对象确实倾斜，但跟踪点漂移导致未报警；
- 对象没有掉落，但遮挡导致错误报警；
- 距离接近阈值时，判定在 True/False 之间抖动；
- 不同视角结果互相矛盾，但系统仍输出确定结论。

SAFE、FAIL-Detect、ReconVLA 和 Foresight 已经证明 conformal prediction 对故障检测有价值，但它们通常输出的是整体失败概率或不确定性分数，而不是**可解释约束谓词的置信区间**。 

这给 CaM 留下了清晰空间：

从“机器人可能失败”推进到“由于锅面倾角约束在 95% 校准覆盖下即将被违反，因此触发稳定动作”。

---

## **3. 点、线、面无法覆盖物理交互故障**

CaM 明确承认其约束元素主要覆盖可通过明显位移和旋转观察到的故障，对以下问题能力有限：

- 施力方向错误；
- 接触力过大；
- 夹持力不足；
- 微小滑移；
- 水流；
- 声音；
- 振动；
- 其他没有显著几何变化的物理状态。 

SafeDiff 等工作已经开始处理力安全，但仍缺少一个像 CaM 一样的：

**从开放式语言任务自动生成多模态物理监控程序的统一框架。**

---

## **4. CaM 的“实时”是经验性的，不是可保证的**

CaM 通过只在子任务开始时运行分割、执行期间只跟踪元素和运行数值代码来降低开销。 

但论文没有系统回答：

- 多个约束同时监控时如何分配周期；
- CPU/GPU 被控制、感知和 VLA 抢占时怎么办；
- 相机帧延迟、跟踪器卡顿后数据多旧仍可使用；
- 关键约束最迟必须多久检查一次；
- 监控任务错过截止时间后是否应该立即停车；
- 低风险约束是否可以降频；
- 多视角和高精度感知何时值得额外计算。

RED 处理了动态推理 DAG，但它的 deadline 来自任务图和系统模型，而不是来自约束的安全余量。 

因此仍有一个较清晰的系统研究问题：

**如何把语义约束距离、故障严重程度和可恢复窗口，转化为监控任务的 period、deadline、criticality 和模型精度要求？**

---

## **5. 缺少直接、统一的主动检测指标**

CaM 自己指出，当时不存在统一的主动故障检测准确率评价标准，因此主要使用最终任务成功率、执行时间和 token 开销进行间接评价。 

但任务成功率混合了多个因素：

- 原始策略是否足够强；
- 检测是否正确；
- 报警是否及时；
- 恢复规划是否成功；
- 执行器是否再次失败。

所以一篇新的工作应当直接标注和评估：

t_{\text{onset}},\quad t_{\text{alert}},\quad t_{\text{irreversible}},\quad t_{\text{failure}}

分别表示：

- 风险最早可观察时刻；
- 监控器报警时刻；
- 最后可恢复时刻；
- 真实故障发生时刻。

然后报告：

- 事件级 Precision / Recall / F1；
- 每小时误报次数；
- 检测延迟；
- 主动预警提前量；
- 最后可恢复时刻前的报警比例；
- 故障原因定位准确率；
- 校准覆盖率；
- 恢复成功率；
- 监控器 CPU/GPU/内存和能耗开销。

这部分可以作为新论文的重要 benchmark 贡献，但由于 SafeManip 和 ForesightSafety-VLA 等新 benchmark 已经出现，仅靠构造数据集还不够，必须与新的监控机制结合。

# **四、最推荐方向一：VeriCaM——验证监控器本身**

## **4.1 核心论文问题**

可以把论文问题定义为：

LLM/VLM 可以生成用于机器人运行时监控的代码，但生成代码可能在对象绑定、坐标系、单位、阈值和时序语义上出错。如何将开放式任务编译为**可验证、可校准、可修复**的监控程序？

可使用如下题目：

**VeriCaM: Verified and Uncertainty-Calibrated Code-as-Monitor for Open-World Robotic Manipulation**

或者：

**Monitor the Monitor: Verified Visual Program Synthesis for Robotic Failure Detection**

## **4.2 不再直接生成 Python，而是生成类型化 Constraint IR**

定义一套中间表示：

```text
constraint KeepPanLevel {
    scope: during(transport_pan)
    entities: pan.surface
    frame: world
    modality: rgbd
    predicate:
        angle(normal(pan.surface), world.z) < 8 degree
    severity: critical
    response: stop_and_stabilize
}
```

IR 至少包含：

|**类型信息**|**作用**|
|---|---|
|Entity / Part Type|防止把锅柄、锅面或整个锅混用|
|Coordinate Frame|区分世界坐标、相机坐标、末端坐标|
|Physical Unit|区分米、厘米、角度、弧度、牛顿|
|Sensor Modality|确保监控谓词确实有可用传感器支持|
|Temporal Scope|before、during、until、after、always、eventually|
|Severity|一般错误、可恢复错误、安全关键错误|
|Response Contract|报警、暂停、减速、回退、紧急停止|
|Deadline|该谓词允许的最大监控陈旧时间|

LLM 只产生受限 AST 或 JSON，不允许直接生成任意 Python；之后再由可信编译器生成 NumPy、C++、eBPF user-space helper 或 ROS2 monitor。

## **4.3 静态验证**

在监控代码执行前检查：

1. 对象和部件是否存在；
2. 谓词参数类型是否匹配；
3. 单位是否一致；
4. 坐标系变换链是否存在；
5. 所需传感器是否可用；
6. 时间逻辑是否自相矛盾；
7. 两个约束是否互相冲突；
8. 阈值是否在物理合理区间；
9. 响应动作是否会违反更高优先级约束。

例如：

```text
distance(object_a, object_b) < 8 degree
```

应在类型检查阶段直接拒绝，而不是等运行时失败。

## **4.4 动态验证与反例驱动修复**

CaM 只用当前状态测试代码分支。新的方法可以在模拟器中自动生成边界状态：

- 倾角在阈值上下变化；
- 交换对象身份；
- 改变相机坐标系；
- 对场景做整体平移或旋转；
- 引入遮挡和点漂移；
- 让深度值出现噪声；
- 随机删除某个传感器；
- 在临界点附近进行 property-based testing。

并定义变形关系：

- 整体平移不应改变相对距离约束结果；
- 同时旋转物体和参考坐标系不应改变相对角度；
- 单位从 m 转 cm 后判定不应变化；
- 无关物体的移动不应影响目标约束。

发现反例后，把反例反馈给 LLM 修复 Constraint IR，而不是简单重新生成一段代码。

这可以形成一个 **counterexample-guided monitor synthesis** 流程：

```text
任务与场景
   ↓
生成 Constraint IR
   ↓
静态检查
   ↓
边界/变形测试
   ↓
发现反例
   ↓
局部修复 IR
   ↓
生成可信运行时监控器
```

## **4.5 不确定性传播与三值语义**

令约束的定量鲁棒性为：

\rho_i(x_t)>0

表示满足约束，负值表示违反约束。

由于跟踪结果并非精确点，而是置信区域 X_t，可定义：

\begin{aligned} \text{SAT}, &\quad \inf_{x\in X_t}\rho_i(x)>0 \\ \text{VIOLATED}, &\quad \sup_{x\in X_t}\rho_i(x)<0 \\ \text{UNKNOWN}, &\quad \text{otherwise} \end{aligned}

这样系统不再被迫对模糊状态输出 True 或 False：

- **SAT**：在当前不确定性范围内必然安全；
- **VIOLATED**：在当前范围内必然违反；
- **UNKNOWN**：需要换视角、刷新分割、降低速度或触发保守策略。

再使用 conformal prediction 校准跟踪置信区间或谓词阈值，使“95% 置信覆盖”具有实际统计含义。这与 SAFE、ReconVLA 的整体失败分数不同，你的方法输出的是：

```text
对象：pan.surface
约束：倾角 < 8°
鲁棒性区间：[-1.3°, 2.1°]
状态：UNKNOWN
原因：部分遮挡导致法向量估计不确定
建议：降低移动速度并刷新侧面相机
```

## **4.6 与已有工作的区别**

- 相比 **CaM**：验证的是 monitor 本身，而不仅是控制策略；
- 相比 **FAIL-Detect/SAFE/ReconVLA**：输出可解释的谓词级置信，而不是单一故障分数；
- 相比 **RoboGuard**：从视觉和物理场景自动接地，而不只是语言安全规则；
- 相比 **RTAMT**：自动生成和验证谓词，而不是监控人工编写的 STL；
- 相比 **SafeManip**：不仅评价已有 rollout，而是在运行时主动报警和干预；
- 相比 **AgentChord**：重点不是恢复图，而是监控条件是否可信。

这条线的论文故事最完整：

**现有工作使用不可信大模型生成监控程序，但没有系统验证该程序。我们提出类型化监控 IR、静态和动态验证、反例驱动修复以及不确定性感知的三值运行时语义。**

# **五、最推荐方向二：RT-CaM——风险驱动的实时监控运行时**

这个方向更贴近你的系统与调度背景。

## **5.1 核心论文问题**

可以定义为：

机器人同时运行控制、感知、VLA 推理和多个故障监控器。在 CPU/GPU 竞争、相机掉帧和网络抖动下，如何保证安全关键约束在最后可恢复时刻之前完成检测？

题目可以是：

**RT-CaM: Risk-Adaptive Real-Time Scheduling for Semantic Robot Monitors**

或者更系统化：

**Semantic Deadlines: A Real-Time Runtime for Generated Robotic Monitors**

## **5.2 将每个约束编译为实时任务**

每个约束 c_i 对应一个 monitor task：

M_i=(C_i,T_i,D_i,L_i,Q_i)

其中：

- C_i：监控一次的执行时间；
- T_i：采样周期；
- D_i：检测截止时间；
- L_i：安全关键等级；
- Q_i：监控质量配置。

Q_i 可以控制：

- 单视角或多视角；
- 低分辨率或高分辨率；
- 轻量跟踪器或完整重分割；
- 只检查几何关系或调用 VLM；
- CPU 或 GPU 后端。

## **5.3 由语义风险生成 deadline**

设当前约束的鲁棒性为 \rho_i(t)，安全边界为 0。若鲁棒性正在下降，可估计：

\hat{\tau}_i = \frac{\rho_i(t)} {\max(-\dot{\rho}_i(t),\epsilon)}

它表示在当前趋势下距离约束违反还有多长时间。

然后设置：

T_i \leq \beta\hat{\tau}_i,\qquad D_i \leq \gamma\hat{\tau}_i

其中 \beta,\gamma<1。

例如：

- 锅几乎水平且稳定：2 Hz 监控；
- 锅倾角快速增加：30 Hz；
- 杯子接近桌面边缘：提高深度相机与跟踪优先级；
- 目标完全静止：降低视角和分辨率；
- 距离最后可恢复状态只剩 100 ms：抢占低风险监控。

这里的创新不只是动态调频，而是：

**从自然语言约束的定量鲁棒性和可恢复窗口中推导实时任务参数。**

## **5.4 混合关键等级与安全降级**

可定义三级监控：

|**等级**|**示例**|**资源不足时行为**|
|---|---|---|
|Safety-critical|人体碰撞、危险力、物体即将跌落|必须保证截止时间，否则减速或停车|
|Mission-critical|抓取稳定、对象身份、步骤顺序|降低其他监控质量，保持检查|
|Best-effort|非关键姿态、效率优化条件|降频、跳帧或暂停|

当系统无法满足所有监控时，不应简单丢弃任务，而是：

1. 降低低风险约束的监控频率；
2. 减少相机视角；
3. 使用较轻量的估计器；
4. 延后非关键 VLM 调用；
5. 对关键约束切换到保守阈值；
6. 无法保证 deadline 时触发 fail-safe。

## **5.5 与 RED 的明确区别**

RED 已经研究动态机器人推理 DAG 和子截止时间分配。 

因此 RT-CaM 不能只说：

我们对相机、分割和跟踪任务做实时调度。

必须强调：

|**RED**|**RT-CaM**|
|---|---|
|deadline 来自端到端推理任务|deadline 来自约束鲁棒性和 time-to-violation|
|目标是 DAG 吞吐与时限满足|目标是最后可恢复时刻前完成报警|
|任务重要性主要由 DAG 定义|重要性由故障严重性、可逆性和语义约束定义|
|deadline miss 是系统性能问题|deadline miss 本身可能触发安全响应|
|通用 DNN 推理任务|可生成、可解释的语义监控谓词|

如果能给出以下保证，系统贡献会比较强：

- 最大监控陈旧时间；
- 最大检测延迟；
- 关键约束的可调度性条件；
- 资源过载时的安全降级上界；
- 对给定运动速度和约束变化率的最小采样频率。

结合你现有的 sched_ext、ROS2、Execution Guard 和工作流系统，这条路线的基础设施复用率最高。论文中应把 CaM 看作一种前端，底层运行时最好还能支持：

- LTL/STL monitor；
- VLA latent detector；
- 视觉跟踪型 monitor；
- 力/触觉 monitor。

这样更有机会形成系统论文，而不是仅仅成为 CaM 的工程优化。

# **六、其他仍有价值的方向**

## **6.1 PhyCaM：从几何元素扩展到物理约束元素**

将 CaM 的点、线、面扩展为：

- contact；
- wrench；
- force direction；
- pressure；
- slip；
- vibration；
- audio event；
- liquid flow；
- temperature。

例如“拉开抽屉”可以被编译为：

\begin{aligned} &\text{contact}(\text{gripper},\text{handle}) \\ \land\;&F_{\min}<\|F\|<F_{\max}\\ \land\;&\angle(F,\text{drawer-axis})<\theta\\ \land\;&\dot{x}_{drawer}>0 \end{aligned}

这样可以区分：

- 没抓住把手；
- 抓住但施力方向错误；
- 力太小无法拉动；
- 力过大可能损坏；
- 抽屉卡住；
- 视觉看似移动但已发生滑移。

要区别于 SafeDiff，必须强调：

不是针对一种任务训练触觉策略，而是从开放式语言任务自动生成跨模态监控程序，并根据传感器可靠性在线组合多个谓词。

这条线创新性较高，但真实传感器、标定和数据采集成本也最高。

---

## **6.2 ForeCaM：对候选动作做反事实约束评估**

不是只监控当前状态，而是对 VLA 输出的候选 action chunks 进行预测：

\hat{x}_{t+1:t+H} = W(x_t,a_{t:t+H})

然后在预测轨迹上执行 CaM 约束：

R(a)= \min_{k=1,\dots,H} \rho(\hat{x}_{t+k})

选择约束违反风险最低的动作，或在执行前进行最小修正。

它需要区别于 Foresight 和 PlayWorld：

- Foresight 主要利用 world-model latent 产生故障判断； 
- PlayWorld 强调从自主交互中学习物理一致的世界模型，并用于故障预测和策略评价。 

新的核心应是：

- 对显式、可解释约束进行未来验证；
- 给出预计违反时间；
- 比较多个候选动作；
- 输出最小约束修复；
- 能解释“哪个未来状态、哪个约束、何时会失败”。

该方向潜力高，但世界模型训练、预测误差校准和计算开销都很大。

---

## **6.3 分布式 Workflow-as-Monitor**

可以把 CaM 从单机器人子目标约束扩展到多机器人工作流契约：

```text
Robot A 完成抓取后，
Robot B 必须在 2 秒内进入交接区域；
交接期间两者不能同时释放；
AGV 离开站点前，机械臂必须处于收拢状态；
共享工位同一时间只能被一个机器人占用。
```

可研究：

- 全局任务约束如何分解为本地 monitor；
- 部分观测和网络延迟下如何合并判断；
- 分布式 monitor 状态是否一致；
- 通信中断时采用何种保守策略；
- 资源锁、工作流阶段和物理约束如何统一；
- 单机器人失败后如何保证重配置仍满足全局契约。

这条线要明确区别于 AgentChord：

- AgentChord 重点是单个长时程操作任务的恢复增强任务图；
- 你的创新必须是**跨执行体、跨资源、带通信与时序保证的分布式监控契约**。

若只是“在工作流图上增加失败分支和 retry”，创新性不足。

---

## **6.4 Monitor-in-the-loop 故障挖掘与自修复**

FATE-VLA 和 DenseReward 主要为策略发现或合成失败。 

可以反过来专门测试 monitor：

- 寻找 monitor 漏报的故障；
- 寻找 monitor 误报的成功轨迹；
- 搜索几何阈值附近的边界场景；
- 搜索对象绑定、遮挡和视角变化；
- 搜索坐标系和单位错误；
- 衡量 predicate coverage 和 temporal coverage；
- 根据反例修复阈值、对象绑定或监控代码。

单独做可能略弱，但作为 VeriCaM 的动态验证模块非常合适。

# **七、哪些方向现在不建议做**

## **1. CaM + VLA 隐层故障检测**

SAFE、I-FailSense、ReconVLA 已经分别覆盖跨任务内部特征、语义错位和校准不确定性。 

除非你的方法能实现：

- 谓词级对齐；
- 可解释原因；
- 约束与 latent 的双向校验；
- 明确的统计保证；

否则难以形成显著创新。

## **2. CaM + 故障解释 + 重规划**

FPC-VLA、RoboFAC、Guardian 和 FailSafe 已经覆盖监督器、故障推理数据和可执行恢复动作。 

## **3. CaM + task graph + 预编译恢复**

AgentChord 与这一构想高度重合，而且已经被 RSS 2026 接收。 

## **4. CaM + 子任务回退或重复执行**

CycleVLA 已经对 proactive self-correction、subtask backtracking 和 test-time decoding 做了完整研究。 

## **5. CaM + LTL/STL**

RoboGuard、RTAMT 和 SafeManip 已分别覆盖语言安全规则接地、STL 运行时监控和 LTLf 机器人安全 benchmark。 

仅仅更换约束语言不足，需要增加：

- 自动视觉接地；
- 类型和单位验证；
- 不确定性传播；
- 反例驱动修复；
- 在线干预。

## **6. CaM + 普通资源调度**

RED 已经覆盖动态机器人推理 DAG、子截止时间和干扰环境中的实时调度。 

必须将创新建立在：

**语义风险 → 可恢复窗口 → monitor deadline → 资源调度 → 安全响应**

这一完整链条上。

# **八、推荐的具体论文方案**

## **方案 A：机器人方向，风险较低**

### **题目**

**VeriCaM: Verified and Uncertainty-Calibrated Code-as-Monitor for Open-World Robotic Manipulation**

### **三项主要贡献**

1. 类型化、带单位和坐标系的 Constraint IR；
2. 静态验证 + 变形测试 + 反例驱动 monitor 修复；
3. 不确定性传播、三值语义和 conformal calibration。

### **实验重点**

- CaM 原始任务：CLIPort、OmniGibson、RLBench；
- 新增 ManiSkill 或 LIBERO 长时程任务；
- 至少一个真实机器人场景；
- 对象交换、遮挡、坐标系错误、阈值变化、跟踪漂移、传感器缺失；
- 与 CaM、FAIL-Detect、SAFE、RTAMT/SafeManip manual monitor 比较。

### **最重要指标**

- monitor 可执行率；
- monitor 语义正确率；
- 约束对象绑定准确率；
- 事件级故障 F1；
- 误报次数/小时；
- 主动预警提前量；
- 原因定位准确率；
- conformal coverage；
- task success；
- 运行时开销。

---

## **方案 B：系统与实时方向，与你的积累最一致**

### **题目**

**Semantic Deadlines: Risk-Adaptive Real-Time Scheduling for Generated Robot Monitors**

### **三项主要贡献**

1. 将语义约束编译为带 period、deadline、criticality 和 fidelity 的实时任务；
2. 基于 constraint robustness 和 time-to-violation 动态调整监控频率及模型质量；
3. 在资源过载、帧丢失和 CPU/GPU 竞争下提供有界检测延迟和安全降级机制。

### **实验重点**

- ROS2 控制、感知、VLA、监控并发；
- CPU stress、GPU inference interference、网络延迟、相机掉帧；
- 单机器人和多工作流并发；
- 固定频率 CaM、EDF/DM、静态优先级、RED-like scheduler；
- Jetson/桌面 GPU/普通 x86 边缘设备至少两类硬件。

### **最重要指标**

- critical monitor deadline miss ratio；
- observation staleness；
- detection latency；
- last-recoverable-point miss rate；
- proactive lead time；
- task success；
- CPU/GPU 利用率；
- 能耗；
- 安全降级次数；
- 调度开销。

若面向 RTSS/EMSOFT，必须给出形式化可调度性或延迟界；若面向 ICRA/IROS/CoRL，则应把重点放在机器人任务成功、预警提前量和资源干扰下的恢复效果；若考虑 EuroSys/ASPLOS，需要把它扩展成适用于多种生成式机器人监控器的通用运行时，而不能只服务于 CaM。

---

# **九、最终建议**

从当前文献格局看，最稳妥的主线是：

**把 CaM 从“VLM 生成一段能运行的监控代码”推进到“编译一套经过验证、具有不确定性语义和运行时保证的监控程序”。**

具体可有两种论文叙事：

- **机器人叙事**：生成的监控器是不可信的，提出 VeriCaM 验证并校准监控器；
- **系统叙事**：监控器即使逻辑正确，也可能因资源竞争而来不及执行，提出 Semantic Deadlines/RT-CaM。

两者可以在同一个系统中共存，但论文主贡献最好二选一。结合你当前的技术积累，更推荐：

**以风险驱动的实时监控运行时为主贡献，以类型化 Constraint IR 和基础静态检查作为前端支撑。**

这样既保留 CaM 的“应用语义编译成运行时信号”思想，又能自然衔接你原有的“应用语义与运行时特征反馈给内核/服务层调度器”研究主线，同时避开 SAFE、FailSafe、CycleVLA 和 AgentChord 已经覆盖的检测、恢复和任务图路径。
