# **结论先行**

路线 B 不应继续围绕“识别工作负载属于哪一类”来设计，而应围绕一个更直接的控制问题：

**系统何时值得偏离默认调度、应该干预哪个任务、采用什么最小调度动作，以及如何限制错误干预造成的损害。**

旧方案的核心链路是：

```text
Feature Data Plane
    → Scenario Identifier
    → Policy Mapper
    → Safety Guard
    → sched_ext Executor
```

路线 B 可以保留观测面和执行面的基本思想，但应彻底替换中间的“场景识别—策略映射”范式。

 文章分析要求.txt

推荐将工作重新定义为：

**面向混合关键任务的语义—运行时信号融合与有界细粒度调度。**

暂定系统名可以使用：

**SemGuard：Uncertainty-Aware Semantic–Runtime Fusion for Bounded Fine-Grained Scheduling**

其核心不是设计一个比 EEVDF 全面更强的通用调度器，而是：

1. 默认保持接近 EEVDF 的公平行为；
2. 只有在存在明确应用目标、检测到可调度问题、证据足够可靠时才干预；
3. 干预只作用于相关 task/cgroup；
4. 干预带有预算、有效期和回退边界；
5. 无法判断时主动 abstain，继续使用基线行为。

这与 ASA 一类“识别工作负载后切换整套调度器”的路线有本质区别。ASA 的输出是 scheduler selection；这里的输出是 task-level bounded action。

# **一、首先重新定义论文要解决的问题**

## **1.1 不再研究“它是什么负载”**

不再以这些标签作为主要输出：

```text
CPU-bound
memory-bound
latency-sensitive
interactive
mixed
```

这些标签描述了任务的部分性质，但不能直接决定调度动作。

新的状态表示应回答四个问题：

|**维度**|**要回答的问题**|
|---|---|
|Objective|什么性能目标重要|
|Symptom|当前目标是否正在受损|
|Cause|损害是否能通过 CPU 调度缓解|
|Confidence|当前判断是否足够可靠|

可以将其称为 **OSCA 状态模型**：

```text
Objective → Symptom → Cause → Action
```

例如：

```text
Objective:
    critical task p99 < 2 ms

Symptom:
    p99 连续三个窗口超过目标

Cause:
    wakeup-to-run delay 上升
    critical task runnable 但未获得 CPU
    CPU contention 明显

Action:
    临时进入 critical lane
    允许有限抢占
    消耗 boost budget
```

相反：

```text
Objective:
    p99 超标

Cause:
    runqueue delay 不高
    任务主要阻塞在 I/O
    观测置信度低

Action:
    no-op / abstain
```

第二种情况非常重要。它说明：

**应用性能恶化不等于调度器应当干预。**

---

## **1.2 推荐的形式化问题**

对每个 task 或 cgroup i，系统接收：

X_i(t)= \{ S_i(t),R_i(t),A_i(t),Q_i(t) \}

其中：

- S_i：应用语义；
- R_i：运行时调度与资源特征；
- A_i：应用级性能；
- Q_i：观测质量和置信度。

系统从有限动作集合中选择：

a_i(t)\in \{ \text{BASE}, \text{PROTECT}, \text{BOOST\_DEPENDENCY}, \text{LOCALIZE}, \text{BATCH}, \text{NO-OP} \}

但必须满足：

\begin{aligned} deadline\_miss &\le D_{\max}\\ background\_slowdown &\le B_{\max}\\ starvation\_time &\le T_{\max}\\ boost\_runtime &\le R_{\max}\\ policy\_change\_rate &\le F_{\max} \end{aligned}

最终研究目标不是分类准确率，而是：

- beneficial intervention precision；
- harmful intervention rate；
- regret to action oracle；
- abstention quality；
- maximum regression；
- rollback latency。

        ┌──────────────┴────────────────┐

┌──────────────────┐          ┌───────────────────────┐

                       ▼

└──────────────────────┬──────────────────────────────┘

这一架构有两个关键原则：

1. **决策模型不进入内核调度 fast path。**
2. **安全控制与收益预测相互独立。**

即使状态估计器或收益模型出错，Safety Governor 仍然可以限制动作。

# **三、各模块的具体设计**

## **3.1 Semantic Contract Plane：应用目标与语义契约**

### **第一阶段不要要求应用深度改造**

语义输入分成三级：

|**来源**|**第一阶段用途**|**可信度**|
|---|---|---|
|启动配置/cgroup manifest|角色、目标、deadline、优先级|高|
|可选 C SDK|phase、dependency、动态 deadline|中高|
|运行时推断|前后台角色、阶段变化|中低|

MVP 阶段主要使用启动配置：

```yaml
groups:
  critical:
    cgroup: /semguard/critical
    objective: latency
    deadline_us: 2000
    criticality: high
    min_cpu_share: 0.15

  helper:
    cgroup: /semguard/helper
    role: dependency
    criticality: inherited

  background:
    cgroup: /semguard/background
    objective: throughput
    max_slowdown: 0.15
```

后续再增加 SDK：

```c
sg_set_phase(SG_PHASE_INTERACTIVE);
sg_set_deadline_ns(2 * 1000 * 1000);
sg_dependency_begin(helper_tid);
sg_dependency_end(helper_tid);
sg_report_latency_ns(latency);
```

### **每条语义必须包含**

```text
scope:
    task / process / cgroup

source:
    config / application / inferred

validity:
    timestamp / ttl / version

trust:
    explicit / inferred / unverified

content:
    objective
    deadline
    criticality
    dependency
    foreground/background
```

不能只传一个永久有效的 `foreground=true`。应用阶段和依赖关系会变化，过期语义必须自动失效。

UFS 已经证明了应用提示通过 eBPF map 影响调度、以及锁依赖语义用于缓解优先级反转的可行性。因此，“应用提示进入调度器”只能作为实现机制，而不能作为单独创新。 

---

## **3.2 Observation Plane：观测面**

### **第一阶段应采集的最小特征**

优先使用与 CPU 调度动作直接相关的信号：

|**类别**|**特征**|
|---|---|
|等待|wakeup-to-run、runnable delay、blocked duration|
|执行|runtime burst、slice consumption、CPU share|
|调度压力|runnable task count、queue occupancy、preemption count|
|迁移|migration count、last CPU、idle wakeup success|
|应用目标|p99 latency、deadline miss、throughput|
|健康度|sample age、event count、lost events|

不要第一阶段就收集几十个 PMU 事件。对于第一个结果，以下信息通常已经足够：

```text
任务重要吗？
任务目标是否受损？
它是否正在 runqueue 中等待？
是否存在可以被临时提升的依赖任务？
背景任务是否消耗了可让渡的 CPU？
```

### **内核数据路径**

高频事件在 BPF 内聚合：

```text
sched_wakeup
sched_switch
enqueue
dispatch
running
stopping
```

用户态按窗口读取聚合结果，不逐事件传输。Ring buffer 只发送：

- 状态变化；
- safety violation；
- rollback；
- hint expiry；  
    -异常事件。

### **PMU 的加入顺序**

PMU 放在第二阶段，用来区分：

- CPU 排队导致的延迟；
- memory stall；
- cache/locality；
- 前端或后端执行瓶颈。

每个 PMU 特征必须携带：

```text
value
time_enabled
time_running
multiplex_ratio
sample_count
sample_age
coverage
```

Tintin 表明 PMU multiplexing 和事件调度会产生不可忽略的观测误差，因此原始 PMU 数值不能作为确定性控制输入。

## **3.3 OSCA State Estimator：动作相关状态估计**

状态估计器不输出 workload 类别，而输出：

```text
state = {
    objective,
    symptom,
    schedulable_cause,
    dependency_state,
    confidence,
    unknown_reason
}
```

示例：

```text
objective:
    latency

symptom:
    p99_violation = true
    trend = worsening

cause:
    runqueue_contention = high
    blocking_dependency = false
    memory_stall = unknown

confidence:
    0.86

decision_support:
    PROTECT is eligible
```

另一个示例：

```text
objective:
    deadline

symptom:
    deadline miss rising

cause:
    critical task blocked on helper
    helper runnable but receives little runtime

confidence:
    0.93

decision_support:
    BOOST_DEPENDENCY is eligible
```

### **MVP 状态估计器**

先使用规则和状态机：

```text
SLO healthy
    → no intervention

SLO violated
+ runnable delay high
+ critical runnable
    → scheduling contention

critical blocked
+ helper runnable
    → dependency inversion

SLO violated
+ runnable delay low
    → unknown/non-scheduling cause

feature stale or insufficient samples
    → low confidence
```

不需要先训练分类器。

## **3.4 Selective Intervention Controller：选择性干预控制器**

控制器分成两步。

### **第一步：Intervention Gate**

先判断是否应该干预：

```text
目标是否受损？
问题是否可能由 CPU 调度缓解？
特征是否足够可靠？
当前是否处于 cooldown？
动作预算是否充足？
```

任一条件不满足：

```text
action = BASE / NO-OP
```

### **第二步：Action Selector**

只在干预资格成立时选择最小动作。

最终版本可以为每个动作预测：

```text
Δcritical_p99
Δdeadline_miss
Δbackground_throughput
Δmigration
Δoverhead
uncertainty
```

决策规则：

a^*= \arg\max_a \operatorname{LCB} \left[ \Delta U(a) \right]

并且：

```text
upper_bound(background_slowdown) <= configured_limit
upper_bound(starvation) <= configured_limit
```

这里的 `LCB` 是收益下置信界。只有保守估计仍然有收益时才执行。

### **模型演进**

|**阶段**|**实现**|
|---|---|
|初步验证|手工规则/FSM|
|数据积累后|小型决策树或 rule list|
|完整论文|每动作 quantile GBDT / conformal prediction|
|不建议|在线强化学习、深度模型、LLM fast path|

训练数据也不再是：

```text
features → workload label
```

而是：

```text
semantics
+ features_before
+ action
→ performance_delta
+ constraint_violation
```

这是一套面向动作效果的数据集。

---

## **3.5 Budgeted Multi-Lane Executor：有预算的多通道执行器**

最终系统使用一个 sched_ext 调度器，不动态替换整套调度器。

### **推荐的四个 lane**

|**Lane**|**用途**|**关键机制**|
|---|---|---|
|CRITICAL|延迟/deadline 任务|wakeup boost、短排队、有限抢占|
|DEPENDENCY|helper/lock holder|临时继承关键性、TTL|
|BASE|默认任务|weighted virtual time、公平基线|
|BACKGROUND|可延迟批处理|较长 slice、较低权重、aging|

### **策略向量**

```c
struct sg_policy {
    uint32_t lane;
    uint64_t slice_ns;
    int64_t  vtime_bias;
    uint64_t boost_budget_ns;
    uint64_t max_wait_ns;
    uint64_t expires_at_ns;
    uint64_t allowed_cpu_mask;
    uint32_t epoch;
};
```

### **核心不是严格优先级，而是预算式优先**

CRITICAL lane 不应无限抢占。建议使用 token/budget：

```text
critical group 每个控制周期获得 boost budget
critical 运行时消耗 budget
budget 耗尽后回到 BASE 行为
下一个周期重新补充
```

Dependency boost 也不是永久提升：

```text
helper 使用 blocked critical task 的部分 budget
dependency 解除或 TTL 到期后立即取消
```

### **防止后台饥饿**

内核侧硬规则：

```text
if runnable_wait > max_wait:
    move task to rescue path

if boost_budget exhausted:
    downgrade to BASE

if policy expired:
    ignore policy and use BASE

if controller heartbeat stale:
    reset all task policies
```

### **快路径职责**

BPF scheduler fast path 只负责：

- 查当前 policy；
- 选择 lane/DSQ；
- 账户 runtime；
- 消耗预算；
- 执行 aging/rescue；
- 检查 epoch/TTL。

不负责：

- 特征模型推理；
- 历史窗口计算；
- 复杂收益估计；
- 在线学习。

---

## **3.6 Independent Safety Governor：独立安全控制器**

安全机制分为三层。

### **L0：动作级回退**

```text
PROTECT → BASE
BOOST_DEPENDENCY → BASE
LOCALIZE → unrestricted placement
```

触发条件：

- 动作未带来预期收益；
- background slowdown 超限；
- migration 或 context switch 异常上升；
- hint 到期；
- confidence 降低。

### **L1：系统策略复位**

```text
清空所有 task override
所有 cgroup 回到 BASE
停止在线干预
继续观测
```

### **L2：调度器卸载**

sched_ext 官方机制支持在调度器终止、发生内部错误或 runnable task stall 等情况下回退到 fair scheduler。这个机制适合作为灾难级保障，但不能替代论文中的 deadline、fairness 和 starvation 安全控制。 

### **Safety Governor 应独立于模型**

模型可以建议：

```text
boost critical task
```

Governor 可以裁剪为：

```text
boost critical task
but:
    max 500 us per epoch
    ttl 1 s
    background min share 15%
    max wait 5 ms
```

具体数值由实验校准，不应写死在系统设计中。

---

## **3.7 Outcome Recorder：结果记录与校准**

每次动作必须生成完整记录：

```text
timestamp
scope
semantic_contract
features_before
feature_quality
state_estimate
selected_action
rejected_actions
decision_reason
safety_clipping
metrics_after
rollback_reason
```

这解决三个问题：

1. 能解释为什么干预；
2. 能计算 harmful decision；
3. 能生成后续收益模型训练集。

# **四、工程实现上的最佳选择**

## **4.1 最快验证与最终实现采用双轨路线**

### **快速验证轨：使用 scx_layered 作为执行底座**

当前 `scx_layered` 已经支持：

- 多 layer 任务组织；
- 不同 layer 的 slice 和 CPU 分配；
- 拓扑/LLC 相关 placement；
- 基于 hint 的动态 layer 切换；
- 新版本中的 PMU 相关能力。

因此，它适合快速验证“语义—状态—动作—收益”是否成立，但这些已有机制本身不能作为论文创新。 

快速验证阶段可以只开发：

```text
semantic sidecar
+ observer
+ controller
+ safety governor
```

执行动作映射为 scx_layered 配置或 hint：

```text
BASE             → normal layer
PROTECT          → latency layer
BOOST_DEPENDENCY → temporary critical layer
BACKGROUND       → batch layer
```

### **最终论文轨：实现最小自定义 executor**

当初步结果证明存在明确收益后，再实现一个精简的自定义 sched_ext scheduler，原因是：

- 需要精确控制 boost budget；
- 需要 task-level TTL；
- 需要 dependency inheritance；
- 需要硬性的 starvation rescue；
- 需要可控的 fast-path overhead；
- 需要清晰的论文机制归因。

最终 executor 不需要包含大量通用调度功能，只需要实现论文真正使用的 3–4 个 lane 和有界机制。

## **4.4 推荐的实验部署模式**

初期使用专用测试机：

```text

    SSH

    controlled experiment workloads
```

- smoke test 使用 partial mode；
- controller/system task 固定到保留核；
- 所有互相竞争的实验任务都由同一个 sched_ext 实例管理；
- 正式实验再使用受控的 full-mode 环境。

# **五、能够最快验证初步结果的 MVP**

## **5.1 MVP 不做什么**

第一版暂时不做：

- 全量 PMU；
- 跨硬件泛化；
- ROS2；
- 复杂 workload classifier；
- affinity/locality 优化；
- 在线学习；
- 强化学习；
- 多个调度器切换；
- 完整应用 SDK。

第一版只验证：

**在混合关键任务中，系统是否能够识别有限的“值得干预窗口”，并通过 per-cgroup/per-task 的有限动作改善关键任务，同时限制后台损失。**

## **5.3 第一版只实现三个动作**

|**动作**|**行为**|
|---|---|
|A0 BASE|默认公平 lane，不特殊干预|
|A1 PROTECT|critical task 进入预算式低排队 lane|

### **第一版控制规则**

```text
if SLO is healthy:
    BASE

    BASE

    BOOST_DEPENDENCY

else if runnable_delay is high and CPU contention is high:
    PROTECT

else:
    BASE
```

动作执行后：

```text
observe K windows

if critical metric does not improve:
    rollback

if background slowdown exceeds bound:
    rollback

if boost budget exhausted:
    downgrade to BASE
```

# **六、初步实验不要先做在线模型，而要先做 Actionability Scan**

这是最重要的工程顺序。

## **6.1 离线动作扫描**

对每一种 phase，分别运行：

```text
EEVDF
BASE
always-PROTECT
always-BOOST
static two-tier
```

得到：

```text
phase
× action
→ critical latency
→ deadline miss
→ background throughput
→ starvation
```

定义一个 phase “可干预”：

\exists a: \Delta critical > \epsilon \quad\land\quad background\_slowdown \le B_{\max}

如果不存在满足约束的动作，则该 phase 的正确输出就是：

```text
NO-OP
```

### **为什么先做这一步**

它直接回答：

是否真实存在调度器可以利用的优化空间？

而不是先花大量时间训练一个模型，最后才发现所有动作都不如 EEVDF。

# **八、完整评估矩阵**

## **8.1 Baselines**

|**Baseline**|**作用**|
|---|---|
|EEVDF|默认强基线|
|Static BASE scheduler|自定义 executor 的中性开销|
|Always PROTECT|证明永久提升的代价|
|Static two-tier|证明固定前后台策略的边界|
|UFS-like policy|应用提示驱动前后台调度|
|scx_layered tuned|当前多 layer 工程基线|
|ASA-like router|整机调度器路由基线|
|Oracle action|离线每 phase 最优动作|
|Full SemGuard|完整系统|

UFS 本身采用 time-sensitive/background 分层以及应用提示，因此一个简单的固定双队列方案不能构成路线 B 的充分对照或创新。

# **九、建议设置的内部 Go/No-Go 标准**

这些是内部工程门槛，不是预设论文结论。

|**项目**|**建议门槛**|
|---|---|
|BASE 对中性 workload 的性能回退|控制在约 3%–5% 内|
|可干预 phase 的 critical p99 改善|至少出现稳定的两位数百分比收益|
|background slowdown|不超过预设预算，例如 10%–15%|
|harmful intervention rate|尽量控制在 5% 以下|
|rollback|1–2 个控制窗口内完成|
|starvation|不出现超过配置上界的情况|
|phase-change|能稳定回到 BASE，而非长期保持 boost|

如果 A1/A2 在可控实验中都无法形成明显 Pareto 改善，则说明问题不在控制器，而在动作空间不足。

# **十、当前最需要避免的设计错误**

## **10.1 不要重新实现“workload classifier + scheduler switch”**

这会再次落入 ASA 的研究范围。 

## **10.2 不要把多 layer、hint 和 PMU 本身写成贡献**

当前 scx_layered 已经具有这些能力。真正的贡献应是：

- selective intervention；
- action-level uncertainty；
- abstention；
- bounded budget；
- wrong/missing semantics；
- harmful decision evaluation。 

## **10.3 不要第一阶段收集所有特征**

先证明：

```text
语义 + runqueue delay + 应用目标
```

能否驱动有收益的动作。

PMU 只在需要区分具体瓶颈时加入。

## **10.4 不要第一阶段从 ROS2 开始**

ROS2 的执行器、DDS、callback dependency、系统噪声会同时引入太多变量。先在 MixBench 中建立因果明确的现象，再迁移到 ROS2。

## **10.5 不要同时开放全部调度参数**

第一版只开放：

```text
lane
boost budget
TTL
max wait
```

slice、vtime、affinity、migration 等参数应逐步加入，否则很难解释收益来源。

## **10.6 不要使用单一 normalized score 掩盖 trade-off**

推荐采用约束式结果：

在 critical p99 或 deadline miss 满足目标的前提下，最大化 background throughput。

而不是把延迟、吞吐、公平性任意加权成一个总分。

# **十一、最终推荐的论文贡献结构**

## **Contribution 1：动作相关的语义—运行时联合状态**

提出 OSCA：

```text
Objective
→ Symptom
→ Schedulable Cause
→ Action
```

同时显式表示：

- source；
- TTL；
- confidence；
- conflict；
- unknown。

## **Contribution 2：具有 abstention 的选择性干预控制器**

系统不是始终选择一个策略，而是在以下条件同时成立时才干预：

```text
目标受损
+ 原因可由调度缓解
+ 动作有预期收益
+ 置信度足够
+ 安全预算允许
```

## **Contribution 3：有预算的 per-task/per-cgroup 多 lane 调度**

提供：

- critical protection；
- dependency inheritance；
- baseline fairness；
- background aging；
- hard runtime budget；
- max-wait rescue。

## **Contribution 4：面向错误决策的系统评估**

重点评估：

- 错误语义；
- 过期语义；
- 低置信观测；
- 未知 workload；
- 非调度型瓶颈；
- harmful intervention；
- bounded rollback。

# **十二、最优执行顺序**

从零开始时，第一批代码不应是 PMU collector，也不应是复杂控制器，而应按下面顺序实施：

```text
1. MixBench + phase driver
2. EEVDF 与静态动作自动化实验
3. Phase × Action 响应面与 Pareto 图
4. scx_layered 上的 BASE / PROTECT / BOOST 原型
5. budget / TTL / starvation rescue
6. 规则式 OSCA 控制器
7. abstention 与 rollback
8. 错误语义和未知状态实验
9. PMU 与收益预测模型
10. 最小自定义 sched_ext executor
11. 真实 workload 和 ROS2
```

整个工作的第一阶段目标应收束为：

**证明系统不是通过“总能找到更好的调度器”取得收益，而是能够识别少量真正可干预的状态，在这些状态下对正确任务施加最小动作，并在其他状态下保持 EEVDF 风格行为或主动不干预。**

这条主线同时满足三个要求：研究问题比原方案更有区分度；工程上可以借助现有 scx_layered 快速验证；初步结果只需要 MixBench、三个动作和一个规则控制器即可得到。
