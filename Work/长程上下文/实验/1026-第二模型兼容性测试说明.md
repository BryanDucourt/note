# 第二模型兼容性测试说明（1026）

**状态**：草稿，先给用户看。

**读者**：实验机上的 GPT。

**依据**：`1026-Colab算力用途-三方讨论.md` 第四节第 1 步。

**要回答的问题**：开源视觉模型 Qwen3-VL 的 8B 和 32B，能不能在我们的真实请求上当"第二个模型"用：
- 输出合不合格；
- 基本能力够不够；
- 对上下文的改动有没有反应。

这一步只测兼容性，不是正式的离线探针。

**分工**：
- **GPT 在开发机上做三件事**：导出请求包、写好笔记本、回收结果后打分。
- **用户在 Colab 上跑笔记本**。

整个测试预计不超过 20 个计算单元。

## 一、导出（开发机）

### 1.1 选哪些请求

只从用冻结提示词跑出的运行里选，以三轮 A→B→A 试点为主（`outputs/paper1-aba-session-20261022-1/runs/0001–0003`）。选的时候可以用 A5，属于实验设计；A5 的内容不进包。

共 30 个：

| 角色 | 个数 | 怎么选 |
|---|---:|---|
| 规划器 | 12 | 最长的输入 4 个；当前头部图里目标认得出（A5）、也就是有明确反证的 4 个；其余随机 4 个 |
| Object | 6 | 当前图里目标认得出的 3 个，目标不在画面里的 3 个 |
| 判断 | 8 | 目标认得出的 4 个，目标不在或很小的 4 个 |
| Spatial | 4 | 随机 |

可选：另从 AI2-THOR 冒烟运行（`lhc-sim2/outputs/ai2thor-smoke-20261026-01/runs/`）里取 6 个，每个角色至少 1 个，单独统计。

### 1.2 每个请求的版本

| 版本 | 怎么做 | 用在哪些角色 |
|---|---|---|
| 原样 | 和当时发给 DeepSeek 的请求完全一样 | 全部 |
| V1 删掉 | 删掉和当前目标有关的 Object 记录 | 规划器、Object |
| V2 丢掉范围 | 把这些记录换成一条"台面上没有<目标>"，证据引用不变；原来没有记录就新加一条 | 规划器、Object |

- 改写只用当时看到的内容，不用真值，规则和第一周 T2 的替换一致。
- 判断看不到记忆，Spatial 这次不做改写，所以这两个角色只有原样。

### 1.3 DeepSeek 在改写版本上的回答

- 原样的回答直接用当时的 `response.json`。
- V1、V2 用冻结的配置重新调一次 DeepSeek，每个版本 3 次，约 108 次调用、300 万 token。

这样两边都能看"同一个模型内部，改动前后差多少"。

### 1.4 包里放什么

全部打成一个 `.tar.zst`，附上 sha256：

| 内容 | 说明 |
|---|---|
| `manifest.json` | 包编号、来源运行、代码提交、提示词和配置的哈希；每个请求的角色、编号、版本，以及文件和图片的哈希 |
| `requests/<编号>__<版本>.json` | 按运行目录里 `request_messages.json` 的格式保存请求体：图片写成 `sha256:` 引用，生成参数照原样（`temperature: 0`、`max_tokens`、`response_format: json_object`） |
| `images/<sha256>.png` | 请求里用到的全部图片 |
| `deepseek/<编号>__<版本>__<第几次>.json` | DeepSeek 的原始回答 |

**不进包**：
- A5、世界位姿、实例名、分数，以及任何评估端字段；
- 打分用的标签另存在开发机上的 `labels_local.json`，不上传。

上传之前，跑一遍现有的信息边界审计。

## 二、Colab 笔记本

由 GPT 写好，用户在 Colab 上运行。

**1027 修改**：开发机上装好了 Colab CLI（0.7.5，已登录），这一节改由 GPT 用它在开发机上直接运行，不经过 Drive，也不需要用户手动操作。要求：
- **用 `.py` 入口代替笔记本，出错即停。** CLI 执行笔记本时，某个单元出错，后面的单元仍会继续跑。
- **开会话后先核对显存和费率**：用 `nvidia-smi` 看显存，用 `colab usage` 看每小时耗多少单元。
  - 8B 用 A100；
  - A100 的显存放不下 32B 的 BF16 时，换 H100；
  - 每小时超过 15 个单元，就停下问用户。
- **预算**：整个测试最多 20 个单元，开跑前后各记一次余额。
- **收尾**：不管成败，最后都要 `colab stop`，并把 `colab log` 导出到运行目录。
- **凭据**：CLI 的登录凭据和会话令牌不进 Git、不进报告，也不进请求包。

**选卡**：一个 A100 80 GB 会话，先跑 8B，再跑 32B，预计 1.5–2 小时，约 11–15 个单元。

**步骤**：
1. 挂载 Drive，把包复制到 `/content` 再解压，核对 sha256。
2. 安装固定版本的 vLLM 和 transformers，选能跑 Qwen3-VL 的版本，写进 `requirements-colab.txt`。
3. 下载 `Qwen/Qwen3-VL-8B-Instruct` 和 `Qwen/Qwen3-VL-32B-Instruct`，记下 revision。
   - 名称以 Hugging Face 上实际的为准；跑不通，就退回 Qwen2.5-VL 的 7B 和 32B，并写明。
   - 32B 先用 BF16，显存不够再换官方的量化版本，量化方式要记下来，作为一个因素报告。
4. vLLM 的设置：
   - 打开前缀缓存；
   - `max_model_len` 按最长请求在 Qwen 分词下的长度，再加输出预算来设，**不准截断输入**；
   - 图片的像素上限记下来。
5. 对每个请求、每个版本：
   - 按原样的参数生成：`temperature 0`、同样的 `max_tokens`、`response_format: json_object`；
   - 修复规则照 `lhc_demo/models.py` 里的：JSON 解析失败时，把原输出和同一句修正提示追加进对话，最多再试 2 次；
   - 每个版本跑 3 次。`temperature` 是 0，所以这 3 次只量不确定性。
6. 每次调用往 `results_<模型>.jsonl` 追加一行，每 50 行同步回 Drive 一次，断了可以按编号续跑。每行记：
   - 编号、版本、第几次、第几次修复；
   - 原始输出、结束原因；
   - 输入和输出的 token 数、时延。

   可选：前 20 个输出 token 的 top-5 对数概率。
7. 环境写进 `env_<模型>.json`：显卡、驱动、CUDA、各包版本、模型 revision、vLLM 参数、开始和结束时间。用了多少单元，由用户从 Colab 界面抄进去。

笔记本里只检查 JSON 能不能解析，用来看进度；正式的合格判定回开发机做。

## 三、回收和打分（开发机）

用户把结果包传回开发机，放到 `outputs/colab-compat-<日期>/`。GPT 用仓库里现有的各角色解析和校验函数打分，口径和在线运行完全一样：

| 量什么 | 怎么量 |
|---|---|
| 合格率 | 各角色第一次就合格的比例、修复后合格的比例；不合格的分类：截断、JSON 坏、工具名不存在、参数不对、缺字段 |
| 基本能力 | 判断：原样请求上的认对率，对照 A5 标签，和 DeepSeek 在同一批图上比较<br>Object：关于目标的记录对不对<br>规划器：和 DeepSeek 选的工具是否一致 |
| 对上下文的反应 | 规划器和 Object 在 V1、V2 下输出变了的比例，以及变化的方向和 DeepSeek 是否一致 |
| 开销 | 每次调用的时延、Qwen 分词下的输入长度、显存峰值、用了多少单元 |

## 四、门槛

每个模型分别判定：
1. **合格率**：修复后达到 98% 以上，同时报告第一次就合格的比例。
2. **基本能力**：判断的认对率比 DeepSeek 低不超过 10 个百分点。规划器和 DeepSeek 的工具一致率报出来，不设门槛。
3. **对上下文有反应**：V2 下至少有一部分输出发生变化，变化方向和 DeepSeek 不系统性相反。

三条都过，就作为第 2 周的第二个模型。只过第 1 条，就换 Qwen2.5-VL 或改用第二家的接口。

报告写一页：两个模型各自的结果，以及建议用哪个。
