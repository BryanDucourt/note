## 一、决策点：48 个

1. **厨房**：测试组的 1、6、12，再从开发组挑 3 个，布局尽量分散，写明挑了哪 3 个。每个厨房用种子 0，两个任务都做。
2. **每个开局 4 个变体**。由测试程序把机器人摆好，可以用仿真信息；手臂都在收起姿态：

| 变体 | PrepareCoffee | SteamInMicrowave |
|---|---|---|
| V0 | 官方开局 | 官方开局 |
| V1 | 底盘沿自身朝向后退 0.4 m | 同左 |
| V2 | 关上装杯子的那个柜门 | 底盘往侧面平移 0.4 m，挑不被挡的那边 |
| V3 | 躯干放到离当前高度远的那一头 | 同左 |

   - 0.4 m 走不了，就取能走的最大距离，不少于 0.25 m；还不行就换一个种子，并记下来。
3. **每个点存**：仿真存档（MuJoCo 状态加工具层的状态）、头部主相机 720×720 的 RGB、深度、分割、目标实体、任务指令。
4. **目标**：PrepareCoffee 是杯子；SteamInMicrowave 是水槽里的菜，也就是第一个要拿的东西。

## 二、真值（只在离线计分时用，不进模型输入）

1. **看得见**：目标在头部图里的可见像素不少于 200。
2. **现在够得着**：从存档出发，用理想区域调一次 pick，看能不能成功；看不见的目标算够不着。
3. **够不着的原因**，从 none、too_far、too_high、too_low、blocked、not_in_view、door_closed 里取一个：
   - 目标在关着门的设施里：door_closed；
   - 看不见、又不是被门挡住：not_in_view；
   - 逆运动学解不出：按目标相对肩部的水平距离和高度，分成 too_far、too_high、too_low；
   - 能解出、但路径会撞：blocked。
   - 分类用的几何规则和阈值，调模型之前写好，放进报告，之后不改。
4. **候选动作表**：从存档出发逐个试，做完以后再试一次 pick，记下哪些动作做完就能拿到目标。
   - 候选：拿目标；开门（只对 V2 的柜门）；底盘前后左右各 0.2 m、0.4 m；转 ±30°；躯干到最低、中间、最高。
   - 每个点至少要有一个这样的动作，没有就换种子，并记下来。
   - 这张表只用来检查变体造得对不对，并写进报告；不拿它给模型的动作打分。

## 三、输入：每个点一次调用

- **图**：头部主相机一张，720×720，不切块。
  - 用 gpt2 挑中的识别模型，按 gpt2 定的阈值和去重规则分出各块；
  - 图上只画编号，类名写在文字里。编号按块的中心从左到右、从上到下排；
  - 画法固定，写明代码版本。
- **文字**：英文，固定模板。不变的部分放前面，变的放后面：
  1. 角色和规则：控制一台移动机械臂，每次只选一个动作；操作类动作不会移动底盘和躯干。
  2. 身体参数：手臂从肩部大约能伸多远、躯干的升降范围、底盘能平移和转动。数值由 gpt3 从机器人模型算出来，所有点都用同一份，写进报告。
  3. 工具，每个一行：pick(mark)、open(mark)、close(mark)、put(mark)、press(mark, button)、move_base(forward_m, left_m, yaw_deg)、set_torso(height_m)。
  4. 输出格式和各字段的含义（见第四节）。
  5. 任务指令（官方原文）、当前躯干高度、手里有没有东西（这批点都是没有）。
  6. 编号列表：`3: mug`、`5: cabinet`……
- **条件 B**：编号列表里，每个编号后面再加三个数，比如 `3: mug, forward 0.85 m, left 0.10 m, height 1.40 m`，以底盘为原点。这三个数取这块区域里深度点的中位数，用相机内外参换算。深度当作建模过的传感器，不用仿真里物体的真实位置。
- 条件 A 和 B 只差这一处。

## 四、输出：固定字段的 JSON

```json
{"target": 3, "visible": true, "reachable_now": false, "why_not": "too_far",
 "action": {"tool": "move_base", "forward_m": 0.3, "left_m": 0.0, "yaw_deg": 0}}
```

- `target`：第一个要拿的物体的编号，看不见就填 null。
- `reachable_now`：不动底盘和躯干，现在能不能拿到。
- `why_not`：取第二节第 3 条那 7 个值之一。
- `action`：一个工具调用。
- 不要求写理由。能用 JSON 模式的就用；格式错了按冻结版的规则修一次，还不对就记成格式错误。

## 六、计分

1. **找对目标**：`target` 是不是绑到目标实体上的那个编号。识别模型没给目标编号的点，单独列出，不算进第 1、4 条的分母。
2. **看得见**、**现在够得着**：和真值比。
3. **原因**：在真值为"够不着"的点上，`why_not` 对不对。
4. **做对决定**：从存档出发，在仿真里真的执行模型选的动作。指物用脚本关口里按区域绑定的规则。分四档：
   - 好：拿成功了；或者做完以后，再试一次 pick 能成功；
   - 有进展：还拿不到，但目标到手臂可达范围的距离（用和第二节第 3 条同一套几何量）缩小了 5 cm 以上；
   - 坏：动作失败、那个距离变大 5 cm 以上，或者去拿、去放、去按够不着的东西或别的东西；
   - 格式错误。
5. **两个关键数**：
   - 说对了但没做对：`reachable_now` 和 `why_not` 都对，动作却不是"好"；
   - 条件 B 比 A 涨了多少，每个模型分开算。
6. **重复的一致性**：GPT-6 的 3 次、DeepSeek 的 5 次、Qwen 的确认，各自报一致率。
