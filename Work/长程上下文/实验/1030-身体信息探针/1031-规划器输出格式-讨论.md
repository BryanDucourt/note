## 二、Claude 的意见（看了用户的看法之后写）

### 1. 同意：不只是输出顺序，整个 v2 提示都围着"看没看到"

查了冻结的 `lhc_demo/planner_v2.py`：
- **任务完成**：一个阶段要 G2（目标出现在当前朝向的画面里）满足才算完成（第 16、22 行）。
- **怎么做**：第 3 步是"选最可能让目标露出来的动作"（第 34 行）。
- **输出**：理由第一句先报 G1/G2 和哪张图里有目标，再说往哪看、往哪走（第 56 行）；预期结果写"会看到什么"（第 60 行）。
- **检索记忆**：给规划器挑记忆的提示，也是"找对找到当前目标有帮助的条目"（第 73 行）。
- **操作**：后来只在输入里加了一个 `holding` 状态（第 82 行），决策的写法没变。

### 2. 数据里的佐证

- 卡住的几批里，理由几乎都从 G1/G2 和"目标最可能在台面上"开头，被挡的记录、空地点、路线都被放在一边。
- 单独追问"什么挡住了、哪里是空地"时，它答得对：输出问的是处境，它就能处理处境。
- 开推理时加"先写三步计划"（每步写动作、预期变化、开始条件），不朝受阻方向的从 10/25 到 15/25。
- THOR 试点里，要先搬东西的阶段大多失败（搬生菜 1/10，容器线索 0/10）。这和"围着看"的写法对得上，但那一批还有工具和识别的问题，不能说就是格式造成的。

### 3. 要想清楚的几处

- **完成判据还在**：找东西的阶段，"看到"就是完成的判据，由判断模块判。要改的是把它当成决策的主线，不是把它删掉。长程任务里，每个阶段的完成判据不一样：看到、拿着、放好、门关上。格式需要一个通用的说法，比如"这个阶段要达成什么、怎么算完成、下一个动作需要什么前提、现在缺什么"。
- **这是新版本**：改输出格式等于做 v3。v2 的所有对照（THOR 试点、BEHAVIOR 闭环、离线门槛）都绑在 v2 上，v3 要有自己的基线。按 1029 的冻结规矩，要离线稳定，每个平台再跑约 5 轮在线。
- **别为 108 设计格式**：要在几种情况上一起检查：108 这种被挡、THOR 的搬放阶段、纯找东西的阶段（看会不会变差）。
- **不开推理时，格式就是它的思考框架**：字段越多，输出越长、越贵，小模型也越难填好。要少而准。

## 四、Claude 的回答和意见（看了用户的草稿之后写）

### 1. G1、G2 是什么

查了 `lhc_demo/planner_v2.py`、`context_v2.py`、`task_sequence.py` 和 1029 试点说明：

| | 意思 | 谁判、什么时候判 | 用在哪 |
|---|---|---|---|
| G1 | 当前这一步拍到的头部图里（包括环视的每一张），至少有一张出现了当前目标 | 判断模块（另一个模型）看图判，每次新观测后判一次，还会做位置复核 | 只告诉规划器"目标在哪张图里出现过"，不算完成 |
| G2 | 目标出现在"最终朝向"那张图里，也就是机器人现在正对的方向 | 同上 | 找东西的阶段，G2 满足就算这个阶段完成 |

- 来历：1028 重写 v2 时，任务定成"依次找到 A、B、再找到 A，每阶段让目标出现在头部画面里"，G1/G2 是为这种"找"的任务设计的。
- **BEHAVIOR**：只有找东西的阶段，全靠 G2 推进（`task_sequence.py`：G2 成功才算阶段完成）。
- **THOR 试点**："找"的阶段按 G2；"搬"的阶段按机器人自己操作的执行反馈推进（放下成功、开过的门关上），放没放对只在离线用仿真核对。
- **RoboCasa 第 3 关**：只测了"找苹果"阶段（G1/G2），搬运成功只在离线记。

### 2. 对草稿的意见

- **"干什么、为什么、预期"**：同意，现在的输出其实也有这三项（工具和子目标、理由、预期结果），问题在"为什么"被规定成先报 G1/G2。补两处：
  - **先核对上一步**：每一步先说"上一步预期什么、实际发生了什么"，再说下一步。卡住时，"预期走近台面、实际走了 0 m"每次都会摆在它面前。这不是针对某个场景的经验，而是对每种动作都适用的通用核对。v2 的"怎么做"第 1 条也写了"比较看到的和预期的"，只是没有放进输出。
  - **预期要能核对**：写成下一步能检查的变化，比如"离台面近了约 1 m""手里拿着生菜""门关上了"，而不只是"会看到什么"。
- **计划**：先放着。可以参考那组开着推理、先写三步计划的结果（10/25 到 15/25），等格式定了再测不开推理时有没有用。
- **各阶段的判据**：同意要按阶段类型分开。完成判据可以来自两处：判断模块看图，或者程序按工具反馈；仿真状态只在离线核对，不进输入。草稿见第 3 小节，等用户改。
- **试点**：同意先试点。新格式等于 v3，要和 v2 在同样的输入上比，而且要在几种情况上都试，不只是 108。

### 3. 各阶段判据的草稿（等用户改）

| 阶段 | 怎么算完成 | 谁来判 |
|---|---|---|
| 找 X | X 出现在机器人正对方向的画面里（现在的 G2） | 判断模块看图 |
| 拿起 X | 手里拿着 X | 工具反馈说拿起成功，加判断模块看图确认是 X |
| 把 X 放到 Y | X 在 Y 上或里面，手空了 | 工具反馈说放下成功，加判断模块看图确认 |
| 打开或关上 Z | Z 开着或关着 | 工具反馈，加判断模块看图确认 |
| 走到某处 | 到了能看到、够得着 Y 的位置 | 里程计和工具反馈，加判断模块看图 |

## 六、Claude 的 v3 草稿（会审前写，不发给 GPT 和 Gemini）

- **任务块**：不再叫 G1/G2，改成"当前阶段"：
  - 阶段类型：找、拿起、放到、打开或关上、走到；
  - 这个阶段怎么算完成（第四节第 3 小节的表）；
  - 现在的状态：判断模块和工具反馈给出的结果，写明各自来源。
- **怎么做**：去掉"选最可能让目标露出来的动作"，换成对每种阶段都适用的写法：
  - 先看上一步的结果和预期对不对得上；
  - 再选最能推进当前阶段完成条件的动作；
  - 上一步没推进的，就要改变做法。
- **输出**，按这个顺序：
  1. `last_step_check`：上一步预期什么、实际发生了什么、对不对得上（对上、没对上、部分）；
  2. `next_action`：工具和参数；
  3. `why`：一两句，说明这个动作怎么推进当前阶段，引用用到的记录或图；
  4. `expected`：下一步能核对的变化。
  - `subgoal` 去掉；计划先不加，等第一轮试点后再测。
- **判据**：按第四节第 3 小节的表。仿真状态只在离线核对。
- **试点**：
  - 离线：在同样的冻结决策点上比 v2 和 v3，不开推理。决策点包括起点 108 的 5 个点、THOR 试点里搬放阶段的点、几个纯找东西的点。
  - 计分按情况分：卡住的点看往空地的移动；搬放的点看动作是不是推进了阶段；找东西的点看和 v2 比有没有变差。
  - 在线：THOR 单住宅试点的三类任务，每类各几轮，和 v2 的试点结果对比。
