# 最小工具链任务说明（1020）：先让找刀实验跑起来

给 GPT 的任务说明。不限定时间，按第二节的顺序推进。代码路径都相对仓库根目录（`lhc-context-demo`）。

**为什么先做这个**：5 轮自主找刀一共 58 次工具调用，全部用在转向（37 次）和前进（21 次）上。没有一轮找到刀，π0.5 一次都没调用。主要卡在移动工具上：
- 前进前要先对准到 8° 以内，每次最多走 0.3 米（`lhc_demo/navigation_guard.py:7-8`、`:60-63`）。
- 连续两次"没确认进展"，就必须先换视角或位置才能再前进（`navigation_guard.py:64`）。"有没有进展"由记忆调用判断，判断一错，动作就被卡住。
- 有任务上下文时，observe、rotate_base、move_base 都必须先写完整的 search_plan（`lhc_demo/task_planning.py:94`）。
- 默认速度 0.08 m/s（`lhc_demo/tools.py:16`）。1800 步在 30 Hz 下是 60 秒，按默认速度全用来前进，也只能走约 4.8 米。

**这一轮的目标**：把移动和环视做到够用，让机器人能走到放刀的台面前、在画面里看清刀。其他工具等跑起来、看到确实需要了再加。

**完成标准**：
- 第四节的单工具测试全部通过；
- 人工试跑 3 轮里，至少 2 轮在预算内走到台面前并看清刀；
- 冻结这一版工具。

**和《实验任务说明（1020）》的关系**：
- 本说明排在那份说明的 B1 基线采集之前。
- 那份说明里的 A1、A3，就是这里的 T1、T2，做完不必重复。
- 那份说明第一节第 6 条要求"工具、导航限制阈值和基线一致"，指的就是这里冻结的版本。

**背景材料**：`docs/experiment-review-20261020.md`，5 轮试验和已知问题。

## 一、共同规范

1. **信息边界不变。** 仿真真值只能出现在评估端。深度属于机器人自己的传感器，可以用，但这一轮只在工具内部使用，不进规划器和记忆调用的输入。
2. **只依据测量。** 新工具什么时候停、什么时候拒绝执行，只能看测量结果：里程计、关节读数、深度、相机标定。不能看任何模型调用的判断。
3. **研究对象不动。** 以下几项都是后续对照的变量，这一轮都不改：
   - 记忆管理的提示词（`MEMORY_SYSTEM`）；
   - 四个记忆库的写入规则；
   - `progress.py` 的计数；
   - 规划器输入里的执行摘要。
4. **旧行为留开关。** 要关掉的限制都做成配置项：新配置默认关闭，旧配置的行为不变。
5. **不改原有文件和记录。** 原有配置文件和已有运行记录都不改，新配置用新文件。
6. **工具返回写清楚。** 每次调用都要返回执行状态、停止原因和实际测到的运动量。新工具的返回字段见第三节。
7. **按 `AGENTS.md` 做。** 源码、配置和文档进 Git；运行记录留在 Git 外，版本记进 manifest；行为改动要做针对性检查。
8. **如实报告。** 失败、跳过的，以及和本说明不一致的地方都写明，不要只报成功。

## 三、要做的事

### T1 重置后重新加载起点

**现状**：`lhc_demo/adapters/behavior.py` 只在启动时调用一次 `evaluator.load_task_instance(instance_id)`，之后的 `reset()` 不重新加载实例。

**要做**：
- 每次 reset 都按配置里的 `instance_id` 重新加载起点。
- 每轮开始时，把起点编号和初始三路画面的 SHA-256 写进 manifest。

**验收**：
- 同一编号连续 reset 3 次，用评估端记录比较：底盘位姿差小于 1 cm 且小于 0.5°，任务相关物体的位姿差小于 1 cm。
- 启动后的第一轮和之后 reset 出来的轮次，同样满足上一条。

### T2 放宽预算

**要做**：
- 新建配置文件，例如 `lhc_demo/configs/search-trial-20.json`：20 次调用、3600 步、1800 秒。T7 的开关也写在这个文件里。
- 原来的 `search-trial.json` 保持不变。
- 常驻会话启动时定下的步数上限，决定了之后 reset 能用的最大预算（`lhc_demo/session.py:74`），所以要按新上限重启一次会话。

**验收**：启动检查输出的有效预算正确；试跑结束时，记录是哪一项上限先触发的。

### T3 评估端记录碰撞和物体位移

**要做**：
- 每次工具调用前后，在评估端比较物体位姿，记下位置变化超过 2 cm 或朝向变化超过 5° 的物体，机器人本身除外。
- 如果仿真接口能取到，再记下机器人和哪些物体发生了接触，地面除外。
- 写进单独的评估文件，例如 `evaluation_contacts.jsonl`，每行对应一次工具调用。
- 这些记录不进任何模型输入、记忆库或规划上下文。

**验收**：
- 故意让底盘撞一把椅子，或推动一个轻物体，记录里出现对应条目。
- 空地上的移动和原地转动不产生条目。
- 说明模型输入的组装代码不会读这个文件，用 grep 或测试都可以。

### T4 试开深度

**要做**：
- 在 `lhc_demo/adapters/behavior_wrapper.py` 的相机配置里加深度，比如 OmniGibson 的 `depth_linear`。现在只配了 RGB（`behavior_wrapper.py:10`）。只开头部相机就够；如果不能单独开，三路一起开也可以。
- 开和不开各测一次：冷启动耗时，以及 300 个仿真步的平均耗时。
- 确认深度的有效范围，以及无效值怎么表示。

**判定**：
- 能开，且每步耗时增加不超过 30%：在 T5 里接入深度停障。
- 否则写明原因，T5 先不用深度。

**验收**：一张开与不开的耗时对照表，一组深度图和对应 RGB 的样例，加上结论。

### T5 新增 move_to_point：走到画面里的一点

**模型给的参数**：
- `evidence_ref`：最近一次观测里的一张头部图，包括 scan 返回的任何一张。更早的图不行。
- `point_xy`：归一化图像坐标 `[x, y]`，和现在 `visual_target.point_xy` 的约定相同。
- `distance_m`：要走的距离。没有深度时必填；有深度时可选。
- `speed_mps`：可选，默认 0.3，上限 0.5。

**代码负责**：
1. **算方位**：复用 `navigation_guard.target_bearing` 的算法，即相机内参加编码器算出的相机位姿（`navigation_guard.py:28-46`）。如果图是 scan 中途拍的，要扣掉拍摄之后底盘又转过的角度，转角用里程计。
2. **转向**：方位偏差大于 2° 时，先原地转到对准。用现有的闭环转动（`lhc_demo/controllers.py` 里 rotate_base 的控制）。
3. **定距离**：
   - 有深度时，读该点附近的深度，换算成到该点的水平距离，再减去停靠距离。如果模型给了 `distance_m` 而且更小，就用模型给的。上限 1.5 米。
   - 没有深度时，用模型给的 `distance_m`，上限 1.0 米。
   - 停靠距离从机身前缘算起，默认 0.4 米。机身尺寸从机器人几何文件里取。
4. **直行**：沿用现有直行控制的加减速逻辑，速度按 `speed_mps`。
5. **停止条件**，满足任何一条就停：
   - 走够了距离；
   - 现有的"没有测到运动"判定：60 步内位移小于 2 mm（`controllers.py` 的 `_stalled`）；
   - 有深度时，机身前缘前方 0.3 米内出现深度点。检查范围是一条通道：宽度为机身宽度左右各加 10 cm，高度从 5 cm 到 1.8 m；
   - 超时，或者收到取消请求。
6. 停下后照常保持姿态、拍新的观测，沿用现有流程。
7. 转向和直行两段都算这一次调用，步数都计入。

**返回**，加在现有执行反馈的 `motion` 字段里：
- 算出的方位角，以及实际转过的角度；
- 计划距离及其来源（`depth` 或 `model`），以及实际走过的距离；
- 停止原因：`motion_target_reached`、`no_measured_motion`、`obstacle_ahead`、`action_window_ended` 或 `stop_requested`；
- 有深度时，还要返回途中通道的最小净空，以及头部相机的近处盲区距离（在 V1 里测出）。

**这一轮不做**：中途重新对准、绕开障碍、路径规划。

### T6 新增 scan：原地环视

**模型给的参数**：无。

**代码负责**：
1. 按头部相机的水平视场角算出朝向数 N，保证相邻两张至少重叠 15%：N = ⌈360 / (0.85 × 水平视场角)⌉。
2. 从当前朝向开始，每转 360/N 度，停稳后拍一张头部图，转完一圈回到起始朝向。
   - 用现有的闭环转动。
   - 转速可以比 rotate_base 的 0.25 rad/s 快，前提是 V1 里的角度误差达标。
3. 每张图记下三项：相对起始朝向的实测角度（左正右负）、拍摄时的步数、相机位姿。
4. 这次观测的"当前图像"就是这 N 张头部图。回到起点后的腕部图可以带，也可以不带。
   - 规划器和记忆调用都要能看到全部 N 张，以及每张的朝向。
   - 需要控制图片总数时，先去掉腕部图。
5. Spatial 的观察点记录要能接收同一次观测里的多张头部图，每张按自己的相机位姿记录。记录规则不变。

**返回**：N、每张的计划朝向和实测朝向、回到起点的残差、总步数。

### T7 关闭依赖判断的限制，更新规划器提示词

**开关**：新增一个配置项，名字自定，例如 `navigation_guard: off | legacy`。旧配置默认 `legacy`，T2 的新配置用 `off`。

**`off` 的行为**：
- 不再执行 `validate_forward_approach` 和 `validate_scan_rotation` 两项检查（`task_planning.py:128-129`）。
- 移动和观察类工具不再强制要求 search_plan（`task_planning.py:94`），包括 observe、rotate_base、move_base、move_to_point 和 scan。规划器给了 search_plan，仍按现有规则校验其中的引用。
- move_base 单次距离上限 0.5 米，专门用来做小幅调整：后退、侧移、短距前进。现有的"没测到运动"停止保留；有深度时，往前走也加上 T5 的通道停障。

**`legacy` 的行为**：和现在完全一样。

**提示词和工具说明**：
- 在 `lhc_demo/tools.py` 的 `TOOLS` 里，加入 move_to_point 和 scan 的说明。
- 在 `lhc_demo/models.py` 的 `PLANNER_SYSTEM` 里，删掉和已关闭检查对应的要求，大约在第 37–62 行，比如"前进前先给 visual_target""对准到 8° 以内""单次最多 0.3 米""两次没确认进展就换视角"。
- 说明三个工具的分工：接近目标主要用 move_to_point；move_base 只做小幅调整；scan 用来一次看清周围。
- 提示词的其他内容不动。
- 提示词随开关切换，两个版本都保留，manifest 记下这一轮用的是哪一版。

**保留**：规划器输入里的执行摘要照常提供，包括 `forward_calls_without_confirmed_progress`，只是不再用它拒绝动作。

### T8 人工选工具的入口

**要做**：
- 新增一种规划器 provider，例如 `manual`，接在 `lhc_demo/session.py:89` 选择规划器的位置。
- 每到规划这一步，把规划器本来会收到的输入写到会话目录，包括当前图像路径、工具清单和执行反馈。
- 然后等人写入一个决策 JSON，格式和规划器的输出相同。收到后照常校验、执行、调用记忆管理、写日志。
- 支持超时和取消。日志里把决策来源标为 `manual`。
- 操作者只根据这个入口给出的图像和文字做决定，不看仿真窗口或场景流。

**验收**：用 `manual` 跑一个 3 步的短轮次（scan → move_to_point → observe）。日志结构和普通轮次一致，并标明了决策来源。

## 四、验收

### V1 单工具测试（不用大模型）

可以沿用 `check_motion` 诊断的机制（`lhc_demo/motion_check.py`），也可以另写诊断。结果统一用评估端的世界位姿核对。

**move_to_point**：
- 空地上选 5 个地面点，方位分布在 −60° 到 +60° 之间。要求：
  - 最终朝向和目标方位相差不超过 3°；
  - 没有提前停下时，走过的距离和计划距离相差不超过 5 cm。
- 朝墙或大件家具走 3 次：
  - 有深度时，在通道净空约 0.3 米处停下，误差不超过 5 cm；
  - 没有深度时，靠"没测到运动"停下；
  - 两种情况都要对照 T3 的记录，如实报告接触和物体挪动。
- 在门口试 3 次：报告是穿过了门，还是停在了门框前。
- 报告每米消耗的步数和每次调用的耗时；有深度时，再报告测出的近处盲区距离。

**scan**：
- 跑 3 次。要求：
  - N 张图齐全；
  - 每张的实测朝向和计划朝向相差不超过 3°；
  - 回到起点的残差不超过 3°。
- 报告总步数和耗时。一次超过 900 步时，先提高转速或减少重叠，再重测。
- 检查一次实际请求的审计文件，确认规划器和记忆调用的输入里都有这 N 张图和各自的朝向。
- 在 scan 的某一张图上选一点，调用 move_to_point，朝向偏差不超过 3°。

**开关**：
- `legacy` 下，旧的拒绝规则仍然生效。
- `off` 下，没有 search_plan 的移动类决策也能执行。

**信息边界**：说明深度、碰撞记录和世界位姿都没有进入模型输入。

### V2 人工试跑

**做法**：
- 用 T8 的入口，从同一个起点出发：实例 0，按 T1 重新加载。
- 跑 3 轮，每轮的预算是 20 次调用、3600 步、1800 秒。
- 这一轮不调用 vla_interact。

**目标**：走到放刀的台面前，在头部图里看清刀，并且评估端算出刀和机器人底盘的距离不超过 1.2 米。"看清"由离线复核的人确认。

**记录**：
- 每轮用了多少次调用、多少步、多少时间；
- 每次工具调用的结果和失败原因；
- T3 的碰撞和物体挪动记录。

**通过**：3 轮里至少 2 轮在预算内达到目标。没通过，就先按失败原因修工具，再重跑。

**注意**：操作者跑第二、三轮时已经熟悉场景，报告里要写明这一点。这一步用来发现工具问题，不算正式的工具链验收。

### V3 规划器试跑

- V2 通过后，换回 DeepSeek 规划器，用同样的工具和起点跑 3 轮。
- 不要求达到目标。要报告卡在了哪一步，并区分两类原因：
  - 工具失败：工具返回了失败原因；
  - 选择或判断出错：工具执行正常，但选的目标或方向不对。
- 根据结果，提出下一个最该加的工具并给理由，比如调整视角或取回旧图。这一轮不实现。

## 七、风险处理

- **深度开不起来，或者太慢**：T5 不用深度，单次距离上限 1.0 米。碰撞情况在 V1、V2 里如实报告。
- **推着物体走**：物体被推着跑时，底盘一直在动，"没测到运动"的判定发现不了。
  - 有深度时，靠通道停障避免；
  - 没有深度时，统计 T3 记录到的推动次数，作为要不要提前上安全检查的依据。
- **scan 太费步数**：先提高转速，再减少重叠。仍然超过 900 步，就报告实测数字，由用户决定。
- **步数先于调用数用完**：报告实测数字，由用户决定要不要再放宽步数预算。
- **关闭限制后，规划器来回转或反复前进**：这一轮不加新的限制，在 V3 报告里记下发生的次数和位置。这属于规划和记忆的问题，正是后续要研究的。
- **现有代码的约束和本说明冲突**：先报告，不要自行绕开。
