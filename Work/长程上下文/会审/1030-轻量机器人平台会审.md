# 1030 会审：找一个有机器人身体的轻量仿真，研究"告诉规划器它有身体"

**起因**：THOR 方案会审（`会审/1030-THOR方案会审.md`）之后，用户 1030 说："我们想研究如果告诉规划器他有一个身体这件事情能不能有帮助，thor没有机器人，有一些behavior里暴露的问题他不会有。不一定要有动力学。加入的新平台。可以。"

**做法**：
- 这是顶层设计，GPT 和 Gemini 都问。同一份背景和问题分别发给两边，各自独立出方案。
- 第一轮不附 Claude 的看法。Claude 的看法在发出之前写好，写完不改。
- 之后整理一致点、分歧和各自的亮点，交给用户。

## 一、用户的看法（原话）

> 我们想研究如果告诉规划器他有一个身体这件事情能不能有帮助，thor没有机器人，有一些behavior里暴露的问题他不会有。不一定要有动力学。加入的新平台。

## 二、Claude 的方案（发出之前写）

**1. 先把"身体信息"说具体。**它分两类：
- **固定的身体说明**：
  - 车身多大，过道要多宽才能过；
  - 每个相机装在哪、能看多宽、能不能抬头低头，例如手上的相机；
  - 手臂够得着多远，夹爪是什么样；
  - 能做哪些动作，各有什么限制。
- **当前的身体状态**：只来自机器人自己的传感器，不用仿真真值。包括：
  - 按里程计估出的位置；
  - 手臂伸着还是收着，手里有没有东西；
  - 刚才哪次移动被挡住了、挡在哪里；
  - 相机有没有被自己的手臂挡住。

**2. 已有的证据**，说明规划器不清楚自己的身体：
- **BEHAVIOR 的手上相机**：两侧相机装在手上，提示里从没说过。规划器在 5/37 次决策里注意到两侧相机被挡住了，但没有理会；也从没用过 move_ee 去移动手上的相机（见 1022 搁置的想法"腕部相机当可移动的眼睛"）。
- **BEHAVIOR 被挡停**：起点 108 那一轮被障碍挡停 38 次。
- **THOR 的相机**：相机固定下俯 30°，规划器却 7 次去开上柜，点都点在图的最上沿，开了也看不到里面。

**3. 实验怎么设**：
- **几组条件**：
  - 不给身体信息（现状）；
  - 只给固定说明；
  - 固定说明加当前状态；
  - 对照组：描述一个错误的身体，或者加入同样长度的无关文字。用来排除"只是提示变长了"。
- **看哪类决策**：要绕开的障碍、够不着的目标、看不到的区域、能不能用手上的相机。
- **量什么**：白费的动作（被挡、够不着、看不到的那些）、任务成败、时间和代价。

**4. 先在现有平台上便宜地试一次。**在 BEHAVIOR 和 THOR 里，挑出和身体有关的冻结决策点，做离线探针：加上身体信息以后，规划器的选择会不会变。真变了，再值得为它专门搭一个平台。

**5. 平台按以下顺序考虑**：
1. **Habitat 3.0 + HSSD**：
   - 好处：
     - 有机器人身体（Spot、Fetch，Stretch 要靠 HomeRobot）；
     - 导航网格按车身大小来算，是运动学的；
     - 有头部相机和手臂相机，柜门、抽屉能开关；
     - 有语义技能：PARTNR 在 Habitat 3.0、HSSD 和 Spot 上，用 LLM 规划器调用导航、拿、放、开这些技能；
     - 速度快。
   - 风险：
     - 在 RTX 5090、CUDA 12.8 上能不能装好，没查到确认；
     - 项目还在不在维护；
     - HSSD 要申请下载权限。
2. **AI2-THOR 的 Stretch 模式**（SPOC 用的就是它，在 ProcTHOR 住宅里）：
   - 好处：成本最低，用的是同一个仿真，我们的适配器大多能复用。
   - 不足：仍然是运动学的瞬移，也不完全是一个"新平台"。
3. **ManiSkill3 / ManiSkill-HAB**：
   - 有物理，但我们并不需要；
   - 语义技能和导航都要自己补，工程量大。

**6. 两周的安排**：
- 第 1～3 天：
  - 在 BEHAVIOR 和 THOR 的冻结点上做身体信息的离线探针；
  - 同时把 Habitat 3.0 的可行性移植限定在 2～3 天内。
- 继续的条件：
  - 能在 5090 上无界面渲染；
  - 每次决策不超过 15 秒；
  - 能复现"被挡住""够不着"这两类失败。
- 做不到就退回到 THOR 的 Stretch 模式。

**7. 风险**：
- THOR 会审的共识是：眼下的瓶颈在任务设计和对照组，不在平台的真实感。再加一个平台，可能重演 1021～1023 刀的识别占掉研究时间那一幕，所以要严格限定时间。
- 身体信息算一类上下文，不是新的记忆库。真要加一个独立的库，按 AGENTS.md 要先和用户讨论。
- 新不新还没查：给规划器写身体说明，在 LLM 机器人工作里很常见。但"系统地量身体信息值多少"这件事有没有人做过，要查。

## 三、GPT 的方案

**我会选 ManiSkill 3 的 Fetch＋ReplicaCAD，给移植三天上限；先用现有 BEHAVIOR 和 THOR 做身体信息的因果对照。** 新平台的价值是便宜、可控地改变身体和相机配置。它目前还不是验证想法的必要条件。

我建议把研究问题收窄成：

> **固定规划模型、工具和感知输入后，明确提供机器人身体约束及当前本体状态，能减少哪些决策错误？这些信息通过记忆生成和传递时，收益损失在哪里？**

"提示里补几句身体说明，成功率提高了"作为独立论文偏薄。值得发展的部分是：**身体信息与任务的匹配、状态变化后的更新，以及信息最终改变了哪些实际行动。**

**一、第三平台的排序：ManiSkill 3、MolmoSpaces、RoboCasa。**

| 排名 | 具体组合 | 最适合你的地方 | 最大缺口 | 我的接入工期估计 |
|---|---|---|---|---|
| 1 | **ManiSkill 3＋Fetch＋ReplicaCAD Interactive** | 已有移动底盘、机械臂、头部和手部相机；场景较小；Python 接口直接 | 需要自己封装受身体约束的语义工具；场景多样性有限 | 最小原型 3 天；研究可用约 5–8 人日 |

| 3 | **RoboCasa365＋PandaOmron** | 厨房操作资产丰富、当前维护明确；适合相机、可达性和操作顺序 | 主要是厨房，跨房间导航不强；默认面向连续控制 | 约 5–10 人日 |

**ManiSkill 3 是我的首选，具体选择主库，先不依赖整个 ManiSkill-HAB。**

- **身体与相机：满足核心需求。** Fetch 实现包含底盘控制、手臂关节、头部转动和躯干升降；默认相机分别挂在 `head_camera_link` 和 `gripper_link`。这正好支持"移动身体改变视野"和"看见但够不到"的实验。代码提供末端位置控制接口，可优先复用已有运动学实现。[Fetch 实现](https://github.com/mani-skill/ManiSkill/blob/main/mani_skill/agents/robots/fetch/fetch.py)
- **场景：够做诊断实验，跨住宅泛化偏弱。** 官方已有 ReplicaCAD、RoboCasa、AI2-THOR 场景加载入口。ReplicaCAD 的公开 84 个布局主要来自同一公寓的不同布置，适合控制实验；论文里应按公寓来源和布局分组，避免把它们写成 84 个独立家庭。[场景接口](https://maniskill.readthedocs.io/en/latest/user_guide/datasets/scenes.html)、[ReplicaCAD 数据说明](https://huggingface.co/datasets/ai-habitat/ReplicaCAD_dataset)
- **安装：中等风险，有直接的 5090 证据。** 官方 issue 中既有 5090 段错误报告，也有维护者在 2026-03-14 表示自己的 5090 可以运行，并指向 Vulkan 排障。我的起点是单环境、CPU 物理、GPU 光栅渲染，随后再决定是否需要 GPU 物理。PyTorch 2.7 已提供 Blackwell 和 CUDA 12.8 支持，但 SAPIEN、Vulkan 和具体 wheel 组合仍需单独确认。[5090 issue](https://github.com/mani-skill/ManiSkill/issues/1323)、[安装说明](https://maniskill.readthedocs.io/en/latest/user_guide/getting_started/installation.html)、[PyTorch 2.7](https://pytorch.org/blog/pytorch-2-7/)
- **维护：当前有较充分证据。** `v3.0.1` 发布于 2026-04-21，主分支最近可见提交为 2026-08-02。[发布记录](https://github.com/mani-skill/ManiSkill/releases)、[提交记录](https://github.com/mani-skill/ManiSkill/commits/main/)
- **资产与许可：** 官方下载器支持 `ReplicaCAD`、`ReplicaCADRearrange`、`ycb` 等资产。主库代码为 Apache-2.0；原始 ReplicaCAD 为 CC BY 4.0；ManiSkill README 对其资产集合另列 CC BY-NC 4.0，实际采用的转换包及机器人资产需要保留各自许可和来源。[代码与资产许可](https://github.com/mani-skill/ManiSkill#license)、[ReplicaCAD 许可](https://aihabitat.org/datasets/replica_cad/)

**ManiSkill-HAB 可以借鉴任务组织，暂不作为运行依赖。** 它确实提供 Fetch、RGB-D、开关和拿放子任务，并于 2025-07 增加导航；但 README 仍推荐专用 `mshab` 分支，同时保留 teleport navigation 的评估路径。最近 2026-05 的提交是 README 更新，和主库当前维护状态应分开判断。其项目元数据声明 MIT，根目录本次未见独立 LICENSE 文件。[MS-HAB](https://github.com/arth-shukla/mshab)、[项目元数据](https://github.com/arth-shukla/mshab/blob/main/pyproject.toml)

**MolmoSpaces 是值得加入的新候选，但我暂排第二。**

它提供 MuJoCo 家庭场景，包含 iTHOR、ProcTHOR 和其他多房间场景来源；有 RB-Y1 移动双臂机器人，传感器系统支持 RGB、深度和本体状态。官方推荐冻结 `v0.2.9`，明确提示主分支正在升级；截至本次检索，2026-10 仍有代码更新。[官方仓库](https://github.com/allenai/molmospaces)、[v0.2.9](https://github.com/allenai/molmospaces/releases/tag/v0.2.9)、[传感器文档](https://github.com/allenai/molmospaces/blob/v0.2.9/docs/sensors.md)

它的优势是**能复用熟悉的家庭资产语义，同时获得完整机器人身体**。但默认低层接口和数据生成流程并非你需要的语义工具。RB-Y1 路线还涉及运动学和可选 cuRobo；官方安装示例中的 CUDA 编译架构列表没有列出 `sm_120`，我不会直接照抄到 5090。先限定经典 MuJoCo 渲染和最少依赖，若必须修 cuRobo 才能完成第一条实验轨迹，就暂停这条路线。[安装说明](https://github.com/allenai/molmospaces#installation)

资产支持按场景懒加载，也提供 Hugging Face 下载。代码 Apache-2.0；非 Objaverse 数据子集列为 CC BY 4.0，Objaverse 集合及单个资产另有许可，部分含非商业限制。第一阶段只取少量 THOR 来源场景，避免下载整个资产集合。[资产获取与许可](https://github.com/allenai/molmospaces/blob/main/docs/assets.md)、[许可说明](https://github.com/allenai/molmospaces#license)

**RoboCasa 的维护最明确，但场景范围与你的长程导航主线稍远。**

当前 RoboCasa365 有 365 个任务、2,500 多个厨房场景和 3,200 多个物体，2026-10 仍发布更新。默认环境工具使用 `PandaOmron`，提供多个相机、腕部相机及深度选项。柜门、抽屉、冰箱等操作很适合研究"站位—观察—伸手"的关系。[官方仓库](https://github.com/robocasa/robocasa)、[环境创建接口](https://github.com/robocasa/robocasa/blob/main/robocasa/utils/env_utils.py)

它基于 MuJoCo，采用普通 CPU 物理与离屏渲染时，CUDA 算子兼容负担较小；风险更多在渲染环境和 RoboSuite 版本配套。官方安装目前要求 RoboSuite `master`，实际接入应固定两边提交。厨房资产约 10 GB；代码 MIT，资产和数据集标为 CC BY 4.0。需要自己补导航、点选目标绑定和语义执行器。[安装与许可](https://github.com/robocasa/robocasa#installation)

**Habitat 功能很贴题，但它已经不满足"2026 年 10 月仍有官方积极维护"这个要求。**

本次 GitHub 查询显示 Habitat-Sim 已归档，README 明确声明 v0.3.4 之后不再由 Meta 内部团队积极开发维护。发布页最新正式 release 仍显示 v0.3.3，日期为 2026-02-12。Habitat-Lab 和 PARTNR 仓库未归档，二者与底层仿真器的状态需要分别看。[Habitat-Sim 状态](https://github.com/facebookresearch/habitat-sim)、[发布页](https://github.com/facebookresearch/habitat-sim/releases)

功能上它仍有吸引力：

- PARTNR 提供 Spot 的运动学配置，以及导航、开关、拿放 oracle skills。
- HSSD 当前有 articulated 场景版本，公开其中 161 个，包含替换后的可动柜子、抽屉和家电；不用再把 HSSD 一概视为静态场景。
- ReplicaCAD 更小，适合第一轮接入。HSSD 为 CC BY-NC 4.0，ReplicaCAD 为 CC BY 4.0；Habitat-Sim、Lab 和 PARTNR 代码为 MIT。[HSSD 数据卡](https://huggingface.co/datasets/hssd/hssd-hab)、[PARTNR](https://github.com/facebookresearch/partnr-planner)

两个具体风险会增加工作量：

1. PARTNR 安装说明固定了较老的 Python、PyTorch 2.4.1 和 CUDA 12.4 组合，需要为 5090 调整；headless Habitat 又依赖 EGL。[安装文件](https://github.com/facebookresearch/partnr-planner/blob/main/INSTALLATION.md)
2. `OraclePickSkill` 采用末端与目标距离判断，代码明确留有"缺少遮挡检查时可以穿墙拿取"的 TODO。直接复用会污染你要研究的身体约束。[拿取实现](https://github.com/facebookresearch/partnr-planner/blob/main/habitat_llm/tools/motor_skills/pick/oracle_pick_skill.py)

如果愿意接受冻结版本、自行维护，Habitat 可以重新进入前两名。按你现在的硬要求，我不选它作为长期新增平台。

**THOR Stretch 值得优先试作扩展；LoCoBot 不够覆盖完整问题。**

- Stretch 已在 AI2-THOR 4.3 的发布记录中进入主分支，当前源码有实际手臂、双相机和碰撞处理。它可能是获得第三种身体的最低成本路径。[发布记录](https://github.com/allenai/ai2thor/releases)、[Stretch 控制器](https://github.com/allenai/ai2thor/blob/main/unity/Assets/Scripts/StretchAgentController.cs)
- LoCoBot 文档主要面向带噪声的导航代理；本次未找到它提供完整移动机械臂语义操作的官方依据。`agentMode="arm"` 对应的 ManipulaTHOR 也需要与 Stretch 区分。[RoboTHOR](https://ai2thor.allenai.org/robothor/documentation/)、[ManipulaTHOR](https://ai2thor.allenai.org/manipulathor/documentation/)
- 你已有 THOR 环境，安装增量较小；主要风险是机器人模式、Unity build 和住宅资产版本的组合。官方主分支最新提交停在 2025-05，正式 release 仍为 2022 年的 5.0.0，本次没有足够依据把它描述成截至 2026-10 仍积极维护。[提交记录](https://github.com/allenai/ai2thor/commits/main/)
- 代码 Apache-2.0，ProcTHOR-10K 仓库也列为 Apache-2.0。原有资产可以复用；若加入 Objaverse，需要另记资产许可。[AI2-THOR](https://github.com/allenai/ai2thor)、[ProcTHOR-10K](https://github.com/allenai/procthor-10k)

我估计 Stretch 最小接入约 2–4 人日，但**换机器人后，要把可达网格执行器与机器人实际碰撞、机械臂可达性重新接起来**。保留原有"自动走到合适位置再完成操作"的强执行器，会大幅压低身体信息的可测价值。

**速度方面，没有候选平台的公开数字能直接回答你的"每次规划决策几秒"。**

| 平台 | 查到的性能证据 | 对你的实际含义 |
|---|---|---|
| ManiSkill 3 | 官方报告 GPU 并行视觉吞吐；公开性能页主要是 RTX 4090、特定任务和相机配置 | 单住宅、双相机、语义动作的延迟待测 |
| MS-HAB | 论文报告家庭交互基准约 4,300 SPS；是并行吞吐 | 不能换算成一次开柜或导航的耗时 |
| Habitat | 官方报告 Fetch＋ReplicaCAD 高吞吐，示例为低分辨率 RGB-D | 高分辨率、碰撞检查和宏动作延迟仍待测 |
| Stretch、RoboCasa、MolmoSpaces | 未找到与你配置相同的可靠端到端数字 | 不承诺具体秒数 |

来源：[ManiSkill 性能说明](https://maniskill.readthedocs.io/en/latest/user_guide/additional_resources/performance_benchmarking.html)、[MS-HAB 论文](https://openreview.net/pdf?id=TvumtJ2gYQ)、[Habitat 性能说明](https://github.com/facebookresearch/habitat-sim)。

我会把移植门槛定为：**单环境、头部和手部各 512×512 RGB-D，短距离移动或一次局部语义操作，仿真＋采图＋序列化 p50 ≤2 秒、p95 ≤5 秒，新增显存峰值 ≤10 GB。** 初始化和 reset 单独计时；规划、判断、记忆 API 单独计时。以上是项目门槛。

**二、实验应先分开固定身体知识与当前身体状态。**

仓库有两个会直接影响设计的事实：

- [planner_v2.py:64](/Volumes/2T/Code/Others/LHC/lhc_demo/planner_v2.py:64) 已有身体段落，包含相机、运动和位姿信息。
- [context_v2.py:103](/Volumes/2T/Code/Others/LHC/lhc_demo/context_v2.py:103) 当前只保留 `head` 图像。

因此，主实验衡量的是**补充具体身体信息的增益**。另做"完全移除身体段落"的消融可以，但要明确它是人为削弱后的参照。

| 信息 | 固定说明 S | 当前状态 D |
|---|---|---|
| 底盘 | 长宽高、能否侧移、转向方式、碰撞会终止动作 | 本轮相对里程计、实际执行位移、当前姿态 |
| 相机 | 安装在哪个 link、视场、固定俯角、是否可独立转动或变焦 | 当前头部角度、由关节和标定计算的相机相对位姿 |
| 手臂 | 关节限制、升降范围、粗略工作空间、单手容量 | 当前关节角、末端相对底盘位置、距关节限位的余量 |
| 工具 | 动作实际改变哪些身体部件 | 最近动作是否完成、挡停或达到限位 |

尺寸和范围从采用版本的机器人模型与执行器取得；不凭机器人名字猜参数。首版固定说明控制在约 200–300 tokens，动态状态约 100–150 tokens。

**禁止混进身体信息卡的内容：** 目标世界坐标、哪个柜子藏了目标、目标是否能抓、最优站位、完整可达地图、评估成功标记。这些会把身体信息实验变成额外场景答案实验。

本体状态采用关节传感器、标定和相对里程计这类可部署来源。仿真世界绝对位姿继续留在执行和评估侧。

主条件采用四组：

| 条件 | 固定身体说明 S | 当前本体状态 D |
|---|---:|---:|
| B | 保留现有 v2 | 保留现有输入 |
| B＋S | 补全 | 不增加 |
| B＋D | 不补全 | 增加 |
| B＋S＋D | 补全 | 增加 |

再在诊断子集加入两个对照：

- **等长对照：** 增加同等长度、真实但与身体决策无关的说明；另外比较等长的通用规划建议。判断收益是否来自篇幅或额外提醒。
- **错配对照：** 交换两种身体配置的说明，或提供明确标记时间的旧状态。观察行为是否随正确身体信息有方向地改变。错配造成损害应作为机制证据，不能充当主要收益基线。

"额外信息量"需要分成两个问题处理：S/D 的有无本来就是实验干预；若要研究**同一信息怎样表达更有用**，另比较"相同本体数据的原始数值"和"简短可操作描述"，不与有无信息的结果混算。

**最有价值的任务是需要先改变身体与环境的相对关系，再完成目标。**

| 任务族 | 具体任务 | 身体信息可能改变的决策 |
|---|---|---|
| 主动观察 | 手部相机被自身或柜沿遮挡；移动手臂后才能看到目标 | 从重复观察转为移动承载相机的部件 |

  * **劣势与风险（一票否决项）**：**5090 安装与维护风险高**。Habitat-sim 对 C++ 编译器、 Magnum 渲染库、Bullet 物理引擎和 CUDA 版本极其敏感，在 5090 + CUDA 12.8 上极易遇到二进制包不兼容而被迫源码编译；且 HSSD/ReplicaCAD 的完整资产下载、许可证申请与版本对齐极其繁琐，一个人维护三个重型引擎（OmniGibson + Unity + Habitat-sim）会拖垮你的发论文节奏。

##### 第四名（不推荐）：RoboCasa
* **优缺点对照**：基于 MuJoCo（robosuite），在 5090 上安装其实很顺畅、速度也快，机器人身体（Panda 移动底盘等）和厨房柜门/抽屉极其逼真。但**场景局限于厨房操作台面**，缺乏跨多房间长程导航结构；且原生接口全部面向低层连续控制（模仿学习/VLA），你要自己手写一套无碰撞导航和"点击图像一点并走过去操作"的语义工具链，工程方向完全错位。

#### 2. 实验设计："告诉规划器它有身体"怎么测？

你现有的系统架构规定"上下文格式已冻结，扩展只能做成开关"，这非常适合做严格的消融实验。

##### （1）身体信息的具体定义（分两层开关）
* **静态身体说明书（Static Embodiment Spec，写在 System/Tool 提示词头）**：
  * **几何与运动限制**："你的底盘半径为 $R$ 米，贴近家具边缘移动会被挡停；每次微小移动（$<0.1$m）可能因摩擦或碰撞无效。"
  * **传感器拓扑与盲区**："你有 3 个相机：头部相机固定朝前（或下俯 $30^\circ$，无法抬头看高于 $H$ 米的物体内部）；左/右腕部相机装在机械手上，当手臂下垂或贴近躯干时会被自身或桌面挡住，可通过调用 `move_ee` 抬高/伸出腕部相机来充当潜望镜观察高处或死角。"
  * **操作工作空间**："你的手臂只能触及距离底盘中心 $[d_{\min}, d_{\max}]$ 米、高度 $[h_{\min}, h_{\max}]$ 米且无遮挡的目标。"
* **动态本体状态（Dynamic Proprioception，每步拼入当前状态文字块）**：
  * **底盘反馈**：上一步位移设定值 vs 实际位移差值、是否触发碰撞挡停（`collision_blocked: True/False`）、当前距离最近障碍物方位。
  * **相机与手臂状态**：当前头部俯仰角、腕部相机当前高度与朝向、视野有效率（如通过深度图简单统计近处贴脸遮挡像素占比："左腕相机 85% 画面被 0.1m 内物体遮挡"）、目标点是否在 IK 可达包络内。

##### （2）实验分组（5 组对照，控制混杂因素）
为排除"提示词变长引起注意力变化"、"工具集改变"和"单纯因为多了环境信息"的混杂，所有组**保持工具列表（JSON Schema）100% 相同**（例如在 BEHAVIOR 中所有组都开放 `move_ee`，哪怕不额外解释它能当相机用）：

1. **G0（Baseline - 盲身体）**：现有系统原貌，无静态身体说明，无动态本体状态。
2. **G1（Length-Control - 长度对照）**：在 G0 基础上加入与静态+动态身体信息**完全等长（相同 Token 数）**的任务无关机器背景文本（如机器人型号编码、无关硬件参数说明），排除提示词长度混杂。
3. **G2（Static-Only - 仅说明书）**：只开"静态身体说明书"，不给每步动态本体状态。测试模型能否仅靠先验说明，主动从图像中意识到遮挡并调用 `move_ee` 或调整站位。
4. **G3（Dynamic-Only - 仅痛觉/状态反馈）**：不给静态全身架构解释，只在每步状态里报客观数值（如 `last_move_blocked: true`、`left_cam_near_depth_ratio: 0.88`）。测试纯状态报错的价值。
5. **G4（Full Embodiment - 静态+动态）**：同时开启说明书与每步本体状态反馈。

##### （3）什么任务会让身体真正起作用？（4 类探针任务）
普通空旷房间的平视找物任务测不出身体的价值，必须专门筛选或构造**"无身体意识必踩坑"**的任务切片：
1. **高处/深处视盲任务（针对 THOR 下俯 30° 与 BEHAVIOR 固定头）**：目标物体放在上层吊柜深处或高架上。无身体意识会贴脸狂点上柜却看不到里面；有身体意识应选择**后退拉开距离**（利用视场角看高处）或**举起腕部相机观察**。
2. **窄道与家具边缘绕行（针对 BEHAVIOR 挡停）**：起点在椅子腿、半开房门或茶几夹角处（如你提到的起点 108）。测试收到挡停反馈和底盘半径说明后，是否能停止"原地微移死磕"，改为后退重规划。
3. **腕部相机自我遮挡恢复（针对 BEHAVIOR 双手相机）**：初始姿态下手臂贴身导致两侧相机黑屏/被挡，且目标在侧面。看是否会主动调用 `move_ee` 把手移开以解锁视野。
4. **操作距离包络边界（针对够不着/站太近）**：目标在桌心或柜子深处，必须把底盘停在恰当距离区间才能触发成功操作。

##### （4）测量指标（对齐你们的"三段兑现"框架）
不要只报最终任务成功率（SR），SR 方差大且信息粒度太粗，必须同时量：
* **病态行为频率（直接指标）**：单轮被挡停次数、连续微小无效移动次数、视野外/看不见内部时的盲目交互次数（如开了上柜看不见还继续点）、腕部相机被挡时调用 `move_ee` 的激活率。
* **三段兑现率（接轨你的核心研究问题）**：
  1. **写下来/感知到**：当发生挡停或相机遮挡时，Object/Spatial 记忆或规划器思考链（若开启简短 reason）中提及身体限制的比例；
  2. **送到规划器**：通过开关精确控制；
  3. **被用上（行为转折率）**：发生挡停/视野受限后的**下一步**，动作分布发生改变的概率 $P(\text{修正动作} \mid \text{身体受阻})$（如从连续 `move_forward` 转为 `turn` / `move_back` / `move_ee`）。

#### 3. 必要性评估：现在需要搭新平台吗？

**结论：完全不需要现在搭新平台，甚至连 THOR 的 Stretch 模式都应该排在预实验之后。**

你在背景里写的三个典型问题（BEHAVIOR 手上相机未利用、BEHAVIOR 起点 108 挡停 38 次、THOR 下俯 30° 开上柜看不到），**全部已经在现有的两个平台上暴露出来了**！
* 你想验证"告诉规划器它有身体有没有帮助"，最直接、最便宜的做法就是：**立刻拿 BEHAVIOR 的起点 108（挡停案例 + 手部相机案例）和 THOR 的上柜任务（7 次盲点上柜案例），改几行提示词和状态注入（即跑通上面的 G0 vs G2 vs G4），跑 5 次重复实验。**
* **成本对比**：在现有平台上验证这个假说，代码改动只需 **0.5～1 天**（纯文本开关与少量仿真状态提取）；而引入并调通一个新仿真平台至少要消耗你 **2～4 周** 的宝贵科研生命，且还会引入新环境的 Bug 混杂。
* **什么时候才需要"新身体"？** 只有当你发现：在现有 BEHAVIOR 和 THOR 默认代理上，"告诉身体信息"确实显著降低了挡停和盲点上柜，但审稿人可能会质疑"THOR 默认代理没有手臂和真实碰撞，BEHAVIOR 又太慢跑不完大规模消融且没有抓取"，这时你再启用 **THOR 的 Stretch 模式** 作为高速、带手臂、带底盘碰撞的中间层，把实验规模扩上去。

#### 4. 相关工作（确定存在的文献与差异）

目前具身 LLM/VLM 规划领域，绝大多数工作默认把身体当成底层控制器的黑盒，**很少有人像你这样结合"信息边界 + 记忆兑现率"去严格量化"身体先验与本体状态文本对高层 VLM 规划器到底值多少分"**。最接近的几类确定存在的工作如下：

1. **执行失败与碰撞反馈类（如 SayCan, Inner Monologue, KnowNo, DoReMi 等）**：
   * **做法**：SayCan 用价值函数（Affordance）过滤当前身体做不到的动作；Inner Monologue 等把底层控制器的成功/失败（如抓取失败、导航受阻）作为文本反馈塞回给 LLM。
   * **与你的差别**：它们只给了"事后动作成败二值反馈"（类似 G3 的简化版），**没有给规划器几何与传感器拓扑层面的"身体说明书"**（比如相机装在哪、视野俯角多少、底盘多宽），更没有研究 VLM 能否主动移动身体部位（如手部相机）来改善主动感知。
2. **多相机与主动感知/具身问答（如 EQA 系列、Active VLM 导航工作）**：
   * **做法**：让智能体决定往哪走、往哪看以收集信息。
   * **与你的差别**：通常把相机当成自由浮动的观察点或绑定在底盘正前方，极少讨论**"手眼耦合（Eye-in-Hand）"与"相机固定倾角带来的视野盲区"**在仅靠图像提示时对 VLM 造成的认知错觉，以及通过显式提示词纠正这种错觉的边际收益。
3. **跨形态/具身感知基准（如 PARTNR, ManiSkill-HAB, EmbodiedBench 等近期基准）**：
   * **做法**：评测不同 VLM 在移动操作任务上的表现。
   * **与你的差别**：偏重端到端成功率评测或任务分解，没有把"身体自知之明（Embodiment Awareness）"拆解为"静态结构说明 vs 动态本体感知"，也没有与长程记忆系统的"写下-送达-用上"三段兑现结合。

*(注：对于 2025–2026 年间是否有完全撞题的小众 Workshop 论文专门做 VLM 提示词里的 URDF/相机外参消融，我不完全确定；但在主流顶会主会层面，将"身体结构说明 + 本体受阻状态"纳入你现有的"长程上下文价值与三段兑现"主线，故事非常统一且新颖。)*

#### 5. 两周行动计划（含限时可行性移植与止损线）

**核心原则：先在现有平台用最小代价拿到阳性结果，再限时试水 THOR Stretch 模式。**

##### 第一周：零新平台，在现有 THOR + BEHAVIOR 上验证假说（Day 1 – Day 7）
* **Day 1–2：实现身体信息开关（G0 / G1 / G2 / G4）**

  * **成功标准**：不动冻结的记忆库主体格式，仅通过配置开关即可切换 4 组上下文。
* **Day 3–5：跑"病态切片"小规模对照实验**
  * 选定 THOR 中包含上柜目标的 5 个任务点 + BEHAVIOR 中包含起点 108 及遮挡场景的 5 个任务点，每点交错跑 5 次重复。
  * **成功标准**：G4（完整身体信息）相比 G0/G1，在 THOR 上盲点上柜次数下降 $\ge 50\%$（且学会后退观察），在 BEHAVIOR 上连续挡停死磕次数下降 $\ge 40\%$ 或开始有效调用 `move_ee`。
  * **放弃标准（止损线）**：如果 `deepseek-flash` 在明确被告知"你刚刚撞墙被挡停了，请勿继续前进"和"上柜太高贴脸看不到，请后退"之后，**依然因为视觉偏见无视文字指令、照旧死磕**（即"送到规划器"但"完全没被用上"），说明瓶颈在于基础模型的图文指令遵循能力而非仿真平台——**立即放弃"加新平台测身体"这条支线**，把它仅作为现有论文里的一个 Case Analysis 小节。

##### 第二周：限时 3 天可行性移植（THOR Stretch 模式）+ 合并主线（Day 8 – Day 14）
* *(仅当第一周拿到显著阳性结果时执行)*
* **Day 8–10：THOR Stretch 模式限时 72 小时可行性移植**
  * 在现有 THOR 5.0 代码库上新建分支，将智能体切为 `Stretch`，接入底盘移动、头部/腕部双相机输出、以及基于距离/可见性判定的语义 `open/close/pick_up/put`。
  * **成功标准**：72 小时内跑通 1 个完整家庭长程任务闭环，单步耗时 $< 5$ 秒，能稳定拿到 RGB、深度、底盘碰撞标志与手臂可达性状态。
  * **放弃标准（止损线）**：如果 72 小时结束时，深陷于 Stretch 手臂逆运动学卡死、物体穿模弹飞或坐标对齐 Bug 无法自拔，**立即回滚并放弃引入第三种智能体**，直接用现有的【THOR 默认代理（测相机倾角与距离） + BEHAVIOR R1Pro（测底盘碰撞与手部相机）】双平台组合完成论文。
* **Day 11–14：将"身体上下文"并入你的第一篇 CCF-B+ 论文框架**
  * 不要把"身体信息"单拧出来写一篇单薄的短文，而是把它作为你现有主线**"具身长程任务中上下文的价值来源与三段兑现"**中的一大核心维度（**外部环境记忆 Object/Spatial vs 内部本体上下文 Embodiment**），直接形成论文里的一个完整实验章节。

#### 总结：明确指出风险与"绝对不该做的事"

1. **绝对不要去配 Habitat 3.0 或 RoboCasa**：在 RTX 5090 + CUDA 12.8 上折腾第三个重型仿真引擎的编译、资产下载和工具链重写，是独狼博士生最典型的"工程逃避科研"陷阱，极易耗掉两个月却发不出论文。
2. **不要把"身体"和"记忆主线"割裂成两个独立课题**：你有两年 3 篇 CCF-B+ 的硬指标，研究问题还没定型。把"本体感知与身体约束"定义为**与 Task/Object/Spatial 并列的第四类关键上下文（Self/Embodiment Context）**，不仅不用改架构，还能让你的"上下文价值与三段兑现"故事立刻变得丰满、独特且极其具身（Embodied）。
3. **警惕 `deepseek-flash` 的空间几何推理上限**：轻量级多模态模型对精确数值（如"底盘半径 0.3m"、"俯角 30°"）往往不敏感，但对**定性因果规则**（如"贴太近看不见高处，需后退一步"、"若提示挡停，严禁再次向同一方向前进"）敏感得多。提示词设计必须把几何参数翻译成**动作条件规则**，否则测出来的会全是假阴性。
