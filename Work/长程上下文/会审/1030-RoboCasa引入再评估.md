## 一、Claude 的看法（发出之前写，写完不改）

**结论**：可以引入，但要有条件。先让现有平台上的探针和一个两天的冒烟移植同时开工；三个前提成立以后，再投入完整的工具层。

**支持的理由**：
1. **身体问题和 R1Pro 同类**：相机装在底盘和手腕上，自己不能转；底盘会被台面和岛台挡住；手臂有够得着的范围；躯干能升降。THOR 上做不出这一类问题。BEHAVIOR 能做，但太慢，每次决策约 43 秒。
2. **快**：MuJoCo 的物理跑在 CPU 上，渲染一张图是毫秒级，跑够做统计所需的次数是可行的。
3. **场景多**：2,500 个厨房、3,200 多个物体，冰箱、柜子、抽屉、微波炉都能开关。适合"东西关在柜子里，早先看到、后来看不见"的任务。
4. **维护活跃，安装风险低**：不用编译 CUDA 算子。

**反对的理由和风险**：
1. **身体信息有没有用，还没有证据**。现有平台上便宜的探针还没跑，先搭平台可能白搭。THOR 会审的共识也是：眼下的瓶颈在任务设计和对照，不在平台够不够真实。
2. **工具层全得自己写，难点在"身体约束要由工具真实执行"**：
   - 导航：底盘沿规划好的路线移动，要做碰撞检查。
   - 点选：从图上一点映射到物体。用 MuJoCo 的分割渲染，执行器可以用。
   - 开关：直接设柜门、抽屉的关节。
   - 拿放：先用机器人自己的逆运动学查从当前站位够不够得着，够得着再把物体吸到手上；放的时候找台面或柜内的空位。
   - 规划器看的图：默认 128×128 太小，要改到 512 以上。底盘上的相机装得很低，本来是给策略学习用的，VLM 看这种视角可能吃力，也许要加一个高一点的"头部"相机。
   - **分寸最费时间**：工具太"神"，比如自动走到合适的位置，身体信息就没用；工具太严，任务又会因为和上下文无关的原因失败。
3. **只有厨房**：没有跨房间搜索。主线里最好的"目标藏起来、隔很久才用到"的任务，在厨房里只能做成"关在哪个柜子里"。
4. **一个人维护三个平台**：上下文 v2 的扩展、执行器、语义工具要三处保持一致，精力摊得太薄。
5. **结果要能迁移**：只在 RoboCasa 上成立的发现，审稿人会问是不是这个仿真的特例。至少要在 BEHAVIOR 或 THOR 上复现其中一类。

**引入前要先成立的三件事**，都可以便宜地检查：
1. 在现有平台上，身体信息能改变规划器的行为。这由探针来测。
2. 在 RoboCasa 的厨房里，VLM 规划器会自然地撞上身体问题，比如被岛台挡、够不着、看不见柜子里面，而且次数够多。用脚本跑两三个任务的小试点就能看出来。
3. 工具层能在 3～5 天内做出来，约束是真实执行的。比如可达性要用机器人的逆运动学来判断，不能用固定的距离阈值。

**我的做法**：
- **同时开工两件事**：
  - 现有平台上的身体信息探针；
  - RoboCasa 两天冒烟：装好；渲染一张 512×512 的机器人相机图；让底盘带碰撞地移动；设一个柜门的关节；把一个物体吸到手上。冒烟只为了估算移植要花多少工夫，不做工具层。
- **放弃线**：安装超过半天；冒烟超过两天；渲染不出规划器能用的图；底盘移动或碰撞不可靠。满足任一条就放弃。
- **之后**：探针有了正面结果，再做完整的工具层，限 5 天。

**和其他候选比**：
- **MolmoSpaces**：把 iTHOR、ProcTHOR 的房子放进 MuJoCo，配 RB-Y1 机器人。能做"同一套房子，有身体和没身体"的对比，还有多房间，这是 RoboCasa 给不了的。但框架年轻、依赖多，主分支在改，cuRobo 的编译架构里没有 5090。值得花一两个小时看一下再定。
- **ManiSkill 3 + Fetch**：公寓尺度，头能转。但有 SAPIEN/Vulkan 在 5090 上段错误的报告。
- **THOR 的 Stretch 模式**：最省事，但还是同一个引擎，移动仍是瞬移。

## 二、GPT 的回答（原文）

**反方最强的理由：第三平台尚未增加不可替代的研究变量，却先增加了一套需要你证明合理的执行系统。**

- **已有失败的归因还不稳。** 当前 v2 已有身体说明，明确写了相机、运动限制和手臂不可用；图像构造还直接过滤非 head 相机。“没用手部相机”应先追查当轮输入和动作权限。反复撞停、开柜后看不到，也可能来自导航工具、视角限制或反馈理解。[身体配置](/Volumes/2T/Code/Others/LHC/lhc_demo/configs/planner-context-v2-behavior-1028.json:3)、[图像过滤](/Volumes/2T/Code/Others/LHC/lhc_demo/context_v2.py:103)
- **工程难点藏在瞬移之后。** 吸附和设关节容易；持续持物、门运动扫掠、手臂可达性、碰撞、放置接触和恢复一致性才费时间。例如 `LoadFridgeByType` 同时检查碗内物品、指定层架接触、夹爪离开。只移动碗会产生新的故障来源。[任务实现](https://github.com/robocasa/robocasa/blob/main/robocasa/environments/kitchen/composite/loading_fridge/load_fridge_by_type.py)
- **审稿人会问收益究竟来自哪里。** 身体事实、动作建议、更清楚的 API 说明、更多图像、执行器自动选站位，都可能提高成功率。跨平台还同时改变任务、视觉、机器人和工具，难以归因。手写距离阈值若刻意制造失败，审稿人会追问它与实际机器人几何的关系。
- **平台数量不会自动转成论文贡献。** 按给定速度，20 个实例×4 组×5 次×30 决策，THOR 约需 33 小时、BEHAVIOR 约需 143 小时，尚未计故障处理。第三平台还会持续增加任务筛选、解释和维护成本。

**我的判断：有条件引入；现在先做现有平台探针，再做一次封顶 24 工时的 RoboCasa 可行性移植。不要同时开发两条线。**

RoboCasa 值得争取的增量，是在同一身体中研究“站位—视角—操作范围”的联合约束。若最后仍然只有转身、接近和看图，继续用现有两个平台更划算。探针门槛应是问题可辨识、动作可执行；零收益也值得保留，避免换平台追正结果。

失败后默认回到两个平台。只有缺少可调身体自由度时，才考虑 THOR Stretch 小范围适配，版本兼容仍待核实。暂不转向 ManiSkill/MolmoSpaces。已确认 ManiSkill 能加载 RoboCasa 场景；其官方场景文档同时写明，大场景尚无现成的完整成功／失败条件和奖励任务，迁移后任务工程仍然存在。[ManiSkill 文档](https://maniskill.readthedocs.io/en/latest/user_guide/datasets/scenes.html)

若引入，最小范围应这样限定：

- **工具：**观察与相机选择、底盘短距平移／转向、躯干升降、开关、单个刚体拿放；腕部观察最多提供少量固定姿态。复用图上点接口、v2 开关和四个独立记忆库。
- **绝对不做：**训练 VLA、通用抓取规划、全厨房自动导航、全任务覆盖、液体／烹饪／精细插入、装有散落物的容器搬运。
- **约束必须作用于动作全过程。** 底盘移动与转向检查全身及持物的扫掠体；拿放检查当前姿态下的 IK、关节限制和路径碰撞；开关检查把手轨迹可达及门的扫掠。通过后允许用运动学执行和吸附。远距离抓取、穿柜取物、穿门移动必须失败。
- **保留规划器的选择。** 执行器可处理碰撞与目标解析，但不得偷偷完成绕行、升降、换视角和寻找最佳站位。数值求解失败单列；工具反馈不给最佳动作答案。尺寸来自碰撞几何，别随意设一个“可达半径”。
- **输入用白名单。** 官方创建入口开启了 `use_object_obs=True`，不能把原始 observation 整包送给模型；身体当前状态限关节读数、选用相机和可追溯的动作反馈。[创建代码](https://github.com/robocasa/robocasa/blob/main/robocasa/utils/env_utils.py)

一个有用的源码细节：agentview 相机挂在 `mobilebase0_support`，该节点具有 0～0.34 m 升降关节；按模型结构，相机应随躯干升降，实际渲染尚未运行确认。这提供了值得研究的视角变化。[相机配置](https://github.com/robocasa/robocasa/blob/main/robocasa/utils/camera_utils.py)、[机器人模型](https://github.com/ARISE-Initiative/robosuite/blob/master/robosuite/models/assets/bases/omron_mobile_base.xml)

任务优先选三类候选：

| 候选 | 身体影响的决策 |

| 柜内取放 | 开门后退、侧移或升降，分别解决遮挡与够不着 |
| 清空冰箱、逐件放到台面 | 门占据通道，持物改变通过条件，往返需要记住操作位置 |

官方有柜内取放和 `PrepFridgeForCleaning`；后者涉及开冰箱并搬出三件食品。[官方示例](https://robocasa.ai/docs/build/html/introduction/basic_usage.html)、[任务代码](https://github.com/robocasa/robocasa/blob/main/robocasa/environments/kitchen/composite/cleaning_appliances/prep_fridge_for_cleaning.py)。具体实例是否真的需要升降、绕门或换视角，仍须筛选；很多默认站位可能已经足够好。

只有厨房，损失的是跨房间搜索、远距离回访和活动类型多样性；家具与物体很多，也无法补齐这些维度。它适合补充操作约束证据。

**对主线有用，但静态身体说明与记忆兑现应分开测。** 静态说明测外给上下文的决策价值；主线更有价值的材料是“哪个站位看得见、哪条路被门堵住、哪种姿态操作成功”，随后是否被写下、检索并改善行动。用同一合法历史整理参考记忆，逐段替换系统写入和检索结果；“被用上”通过删除该信息后的动作及闭环结果判断，别依赖模型理由。

身体说明建议先做“固定事实×当前状态”的 2×2，对齐总长度、图像和工具反馈；动作规则另组比较，避免把“先退再开门”等策略混进事实。每点五次用于估计 API 波动，独立实例仍按任务和布局计算。

## 三、Gemini 的回答（原文）

## 1. 唱反调：现在不该引入 RoboCasa365 的五个硬伤

1. **方法论自相矛盾与“规则泄漏”混杂（最致命）**
   RoboCasa 的核心价值在连续物理操控（背景四、五），而你计划改成“直接设关节开关 + 吸附/瞬移拿放”（背景六）。一旦剥离连续控制，什么算“够不着、站太近、被门挡”就完全取决于你在工具层手写的几何前置条件；随后你又把同一套身体参数写进上下文喂给规划器。这会制造严重的**循环论证混杂**：实验测的不再是具身空间推理，而是大模型能否读懂你手写的 wrapper 阈值。
2. **丧失基准背书，白交新平台工程税**
   接入知名基准的最大回报是与公开基线直接比分数。但你不打 agentic 榜（决定本身完全正确），又用运动学魔改替代底层控制（背景五、六），导致你的结果与社区任何 VLA/连续控制基线都不可比，所有对照仍得自己跑——付出了重型基准的接入成本，却拿不到基准公信力。
3. **对主线产生“单房间偏置”，削弱 Spatial 记忆价值**
   主线核心是长程任务中四库记忆的三段兑现（背景二）。RoboCasa 只有单房间厨房，且底盘左中右三路相机视野宽（背景五），几乎没有跨房间拓扑探索与视线完全隔断的长程折返，会人为压低 `Spatial` 记忆的兑现上限，并与 THOR 的 iTHOR 厨房高度同质。
4. **工程黑洞被严重低估**
   该平台无现成导航和语义工具层，且强依赖无固定发版的 `robosuite master`（背景五）。你要从零补齐：含动态障碍（打开的柜门/洗碗机门）的碰撞导航、默认 `128×128` 低清相机升分辨率与实例掩码对齐、以及瞬移/改 `qpos` 后的物理稳定性。在 MuJoCo/robosuite 体系中，直接改 `qpos` 或瞬移物体极易触发穿模弹飞，或因缺少夹爪接触力导致内置 `_check_success()` 不触发（未核实 RoboCasa365 全部任务的成功判定代码）。
5. **审稿人追问与毕业时间账算不过来**
   - **审稿人会直接问**：①“身体约束来自物理引擎，还是来自作者自定义工具的人工阈值？”②“从 THOR 换到 RoboCasa 同时变了渲染、任务和工具实现，如何剥离工具层差异与身体形态效应？”③“只为一个上下文开关（背景二），为何选纯厨房测长程记忆？”
   - **时间成本**：博三末单人作战、两年需 3 篇 CCF-B+（背景一），扣除审稿周期，第一篇必须在 3～4 个月内投出。当前主线尚未定型（背景二），为一个“不单独成题的子问题开关”新建第三平台，再乘上每点 5 次交错重复的评测开销（背景一），极易拖垮第一篇截稿。

## 2. 独立判断

**结论：第一篇主线论文坚决不引入 RoboCasa365。** 现有方案里“冻结 v2 开关、加等长无关文本对照、5 次交错重复、放弃打榜”都没有问题，唯独“现在上第三平台”错了。

**替代方案：保留现有双平台；若需强化身体对比，在 AI2-THOR 5.0 中启用 `Stretch` 模式（与默认代理同场景对照），并在 BEHAVIOR-1K 中开放 R1Pro 手腕相机的离散观测视角。**
- **理由**：
  1. **同引擎消融更干净**：THOR 已有 `10s/步` 管线、可达网格和实例掩码（背景三）。切 `Stretch` 模式（未核实 THOR 5.0 中 Stretch 与你现有工具封装的接口差异）可在**同一批 ProcTHOR 多房间住宅与 iTHOR 厨房**中对比“默认圆柱代理 vs 矩形底盘+伸缩臂+双相机”，彻底消除跨引擎混杂，同时保住主线必需的多房间 `Spatial` 记忆。
  2. **现有双平台证据已够发好文**：BEHAVIOR 挡停 38 次且不用手腕相机、THOR 盲开上柜 7 次（背景三），已是极佳的自然具身失败样本，双异构平台完全满足 CCF-B/A 的实验跨度。

## 3. 如果坚持引入 RoboCasa365

- **最小工具层边界**
  - **只做 3 个原语**：① `move_base(x, y, yaw)`：静态几何体生成 2D 栅格跑 A*，行进中每步调 MuJoCo 原生碰撞检测（未核实 robosuite 具体封装名），撞上打开的门扇即停并返回受阻状态；② `set_posture(torso_h, wrist_preset)`：控制 `0~0.34m` 躯干升降 + 3～4 个无碰撞手腕相机观测姿态（收拢、仰看高柜、俯看深抽屉、平视）；③ `interact(op, cam_id, u, v)`（`op ∈ {open, close, pick, place, toggle}`）：渲染升至 `512×512`，用对应相机的深度+实例掩码反投影 3D 目标点。
  - **绝对不做**：12-DoF 连续控制、编译 `cuRobo`/MoveIt、物理夹爪闭合抓取（`AnyGrasp`）、外部视觉模型（`SAM3`）、全量适配 365 个任务（只筛刚体开关拿放类，避开流体/精细旋钮，未核实具体任务清单）。
- **如何由工具真实执行身体约束（防假规则、防无关失败）**
  - **视觉约束靠真实视锥**：只能点 4 路相机实拍画面上的像素；不升躯干或不切手腕姿态就拍不到上柜/深抽屉内部，自然拿不到目标掩码。
  - **可达性靠真实雅可比逆解（IK），禁写距离阈值**：在当前底盘位姿与躯干高度下，对 Franka 7 轴跑纯运动学 IK + 关节限位与环境碰撞检查（未核实 robosuite master 内置 IK 调用细节）。IK 无解或碰柜体则失败；有解则**跳过手指闭合动力学**，直接运动学吸附（weld）或放置后跑短步静置。
  - **开门干涉靠分步扫掠**：`open/close` 分 15～20 步递增关节 `qpos` 并每步查碰撞；站太近时门扇扫到半途撞上 PandaOmron 底盘即卡住，真实复现身体阻挡且零抓滑噪声。
- **高价值任务与纯厨房损失**
  - **真正吃身体的任务**：垂直跨度大+宽门扇+窄过道的组合任务，如“装冰箱”（宽门扇撞底盘+深层遮挡）、高吊柜取物转存下层洗碗机/烤箱（强依赖 `0~0.34m` 升降、手腕视角与过道门扇避让）。
  - **只有厨房的损失**：丢失跨房间长程导航，`Spatial` 记忆退化为局部柜位记忆；易被质疑结论过拟合标准橱柜模数。
- **对主线的价值**：对 `Object` 记忆（多闭合柜体内容物追踪）和 `Experience` 记忆（记下“某柜需升躯干/某门打开堵过道”并在后续兑现）有用；对 `Spatial` 记忆帮助弱。
