## 一、Claude 的方案（发出之前写好）

**A. 底层：主线用乙，也就是 RPent 加冻结的 RLDX-1，把特权信号都藏起来。**
- **理由**：
  1. 用户的草稿要官方任务、要和主流比、要看到效果。走乙，现成的外部基线和官方指标都有：RLDX-1 单独跑 30.0；RPent 能看到特权信号时是 57–59。
  2. 不用训练。旋钮、水龙头、电器门这些操作 VLA 都会，甲要我们一个一个写。
  3. 身体还在：RPent 的底盘和手臂原语（move_base、navigate_to、move_to、rotate_pitch）由规划器来调。"把身体当工具用"对应到"调 VLA 之前，把身体摆在哪里"，可以量。
- **代价**：
  - 算力：VLA 约 7B，放在 A100 上，或者占满 5090；
  - 回合长，规划器花钱多；
  - 底层失败多：RLDX-1 在没见过的组合任务上只有 5.0；
  - RPent 的代码还在快速变化，要固定版本。
- **甲先放着**：代码留着，以后要分开"规划器的错"和"底层的错"时再用。丙不做。

**B. 判完成：特权信号全部藏起来。**
- success、terminated、task_progress、success_criteria 这四样，规划器都看不到。
- 规划器自己调 finish，或者用完预算；官方 `_check_success()` 在回合结束后离线算。
- 另外离线记两件事：每一步官方判定是真是假；规划器在哪一步停的。这样能分出"说早了""做到了还没停""没做到"。
- **基线**：RPent 藏掉信号以后的版本。RPent 公布的数字是看得到信号时的，只能当参考，不能直接比。
- **这样一来**："看不到特权信号时，怎么知道自己做到哪了"就成了核心难点，正好落在上下文的"任务进度"那一部分。

**C. 规划器**：
- **主结果用强模型**：主流的数字都是这样报的，基线也就一致。
- **"小模型也能规划好"放到第二条线**：比如 Qwen3-VL-8B 或 deepseek，看我们的上下文对小模型帮助是不是更大。
- **输出形式要注意**：Codex、Claude Code 这类编程智能体自己管上下文，会读文件、也有自己的对话历史，我们要研究的上下文变量会被它冲淡。所以实验用 RPent 的 `api` 接法，上下文由我们控制；编程智能体那几行只当参考基线。

**跑通的新定义**：
1. **先只跑 VLA**：用任务原文直接调 RLDX-1，跑几个原子任务，对一下公布的原子任务 60%，以此确认装对了。这一步不涉及规划器，也就没有特权输入的问题。
2. **再跑一小片**：比如 3 个原子任务、2 个见过的组合任务、1 个没见过的组合任务，各 2 个种子；信号全藏，用一个规划器。
3. **通过的标准**：从头跑到尾；官方判定只在离线记；规划器输入的审计里没有特权信息；记下每次的用时和 token。
4. 看了耗时和成本，再定完整基线跑多大。

**上下文**：
- RPent 自带的跨回合记忆，是用带成功标签的探索做出来的。主比较里先关掉，或者固定不动、照规则申报。
- 我们改的放在回合之内：世界、身体、任务进度。

**其他**：
- **BEHAVIOR**：以后再说。CaP-X 有 R1Pro 的接入，到时候再看。
- **THOR**：停。
- **`AGENTS.md`**：架构定了以后再改四库那一条。

**风险**：
1. VLA 的失败太多，上下文的作用被噪声淹没；
2. 时间和钱；
3. 藏掉信号以后，基线可能低到底，没法比；
4. 撞车：Harness VLA、PhyAgentOS 已经展示过"套一层框架"的收益，我们的新意必须落在"没有特权信号时，回合内的上下文"。
