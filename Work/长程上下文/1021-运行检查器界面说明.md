# 运行检查器界面说明（1021）

给实验机上 GPT 的说明。代码路径相对仓库根目录（`lhc-context-demo`）；行号对应冻结版 `157ba3a`。

**要做什么**：一个只读页面，在运行过程中和运行结束后都能看到三样东西：每一轮看到的画面；规划器和各个记忆调用的输入、输出；四个记忆库的记录，以及每一步改了什么。

**设计稿**：在 claude.ai 上，你打不开。用户会从画布导出三张图给你：单步数据流、一次模型调用的详情、一条记录的演变。版面和功能以本文为准。

**基础**：在现有的只读页面 `lhc_demo/viewer.py`（端口 8768）上扩展，不另起炉灶。

**时机**：
- 读旧格式的部分现在就可以做。
- 按调用显示四路记忆调用，要等记忆分库合入，因为那时审计格式会变（见《记忆分库修改清单（1021）》第四节）。

## 一、原则

1. **只读。** 不写会话目录，不发控制命令（stop、reset 仍走原来的命令行），也不进任何模型。服务只绑定 127.0.0.1。
2. **显示每一轮实际看到的画面**：头部、两路腕部，以及 scan 拍的每一张。
3. **区分"选中了"和"实际送进了请求"。** 以审计里的实际输入为准。注意：没有挑选记录时，`context.py:375` 的 `view` 会自动补上最近的记录。
4. **旧运行按 `legacy_unified` 显示。** 旧运行里四个库的记录出自同一次调用，不能显示成四个独立来源。
5. **评估数据默认不显示。** 包括碰撞记录、A5 可见性、离刀的距离。人工操作的轮次（provider 为 `manual`）里，评估视图不能打开，免得操作者看到特权信息。
6. **文件可能还没写完。** 读不到完整的 JSON 就先跳过，下次轮询再读。

## 二、三个页面

### 1. 单步数据流（主页面）

- **顶部**：
  - 会话、轮次和状态（运行中、已结束、`robot_fault` 等），当前步数和调用次数；
  - "跟随最新"开关；选择轮次的入口。
- **画面条**：
  - 按采集顺序排出每一帧头部画面的缩略图；相邻两帧之间写上这一步执行的工具和结果，结果分已完成、受阻、故障三种。
  - scan 那一步要显示它拍的全部画面，以及每张的朝向。
  - 点任意一帧，就切到那一步。
- **决策链**：从左到右四段，段与段之间用箭头连起来：
  1. 动作前的画面：头部大图，下面是两路腕部小图。头部图上画出规划器选的目标点（`move_to_point` 的 `point_xy`），以及冻结检查条件的区域框。
  2. 规划器：
     - 输入：用了哪几张图、哪些记忆条目（每条带来源）、执行摘要；
     - 输出：工具、参数、理由、冻结的检查条件。
  3. 执行结果：对准角、实际走的距离、停止原因、净空。
  4. 动作后的画面。
- **记忆更新**：每个调用占一行，从左到右是：
  - 送进来的东西，按来源类型上色：画面、工具反馈、冻结条件、目标查询、本库记录、历史附图；
  - 没有送进来的东西；
  - 输出摘要；
  - 写进的库，每条标出新增、修改、未变或被拒。

  Task 那一行标明"程序维护"。所有行最后汇总成一栏"下一步规划器看到的"；同一帧画出的多条记录，要标出"按 1 份证据计"。

### 2. 一次模型调用的详情

- **送进来的**：
  - 实际附上的图像缩略图，每张标明帧编号、采集步数和哈希；
  - 历史附图，以及当时的区域框；
  - 其他输入，比如目标查询、本库记录的条数。
  - 另列一份没有送进来的东西。
- **输出**：
  1. 第一步列出的特征：在当前画面上画出每个特征的区域框，编号和列表一一对应。
  2. 第二步写的记录：依据、类别、身份判断、负证据、操作就绪状态等。
- **校验与审计**：
  - 引用检查和写入范围的结果；有没有引用没送进来的证据；被拒的更新及原因；
  - 提交前后的版本号，以及同一批次里的其他调用；
  - 模型、提示词哈希、耗时、token、格式修复次数；
  - 可以打开原始输入和原始回复的 JSON。

### 3. 一条记录的演变

- 选一个库和一个 key，按版本逐条列出：当时的画面、写入这一版的调用、记录原文、依据。
- 同一次调用写进其他库的内容也并排列出：
  - 旧格式：并排列出同一次调用写进其他库的记录；
  - 新格式：并排列出同一帧下其他调用写的记录，并标明是不是同一帧。
- 可以输入一个词，比如 counter，用矩阵标出每一版里这个词出现在哪几个库。

## 三、数据从哪里来

| 内容 | 文件 |
|---|---|
| 时间线 | `context/task/tool_calls.jsonl`、`context/task/tool_results.jsonl` |
| 每一帧 | `evidence/obs_*/observation.json`：图像引用、采集步数、哈希；图像在同一目录下 |
| 规划器 | 旧格式：`audit/planner/*_input.json`、`*_response.json`；新格式按 `batch_id`、`call_id`、`role`、`attempt` 定位 |
| 记忆调用 | 旧格式：`audit/models/memory_manager/<编号>/` 下的 `input.json`、`response.json`、`request_summary.json`；新格式见分库清单 |
| 各库 | `context/<库>/history.jsonl`，Experience 是 `cases.jsonl`（`context.py:36`）；`records_state.json`；`selection_history.jsonl`（`context.py:184`）；Task 的程序更新事件 |
| 评估视图 | `evaluation_contacts.jsonl`、A5 的 `evaluation_observations.jsonl`、`evaluation.json` |

## 四、技术要求

- 沿用 `viewer.py` 的做法：用标准库写 HTTP 服务，前端是一个静态页面，不引入新的重依赖。
- jsonl 增量读取，每 1 到 2 秒轮询一次；只有出现新文件时才重新加载图片。
- 图片路径检查沿用现有做法（`viewer.py:92` 起），只允许读运行目录下的 `evidence`，防止路径穿越。
- 一轮里有几百张图时，缩略图按需加载。

## 五、验收

1. **旧运行**：用数据包里的 0025 打开三个页面。
   - 画面条显示 obs_000000 到 obs_000010 的头部画面，以及每一步的工具和结果。
   - 在"一条记录的演变"里输入 counter，矩阵应该显示：调用 000000、000001 里有 3 个库出现，000002 到 000004 里四个库都出现。这和人工核对的结果一致。
2. **新结构的运行**（分库合入以后）：
   - 四路调用的输入和输出都看得到；
   - 同一帧的多条记录标出"按 1 份证据计"；
   - Task 显示为程序维护。
3. **跟随最新**：运行中打开"跟随最新"，新的一步在 5 秒内出现；停在某一步查看时，不会被刷新打断。
4. **人工轮次**：manual 轮次里打不开评估视图。
5. **scan**：在一轮带 scan 的运行里，scan 那一步显示 5 张图和各自的朝向。
6. **只读**：页面不发出任何写请求；用一次代码检索说明，服务端没有写会话目录的代码路径。
