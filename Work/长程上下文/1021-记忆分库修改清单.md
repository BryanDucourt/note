# 记忆分库修改清单（1021）

给实验机上 GPT 的程序修改清单。代码路径相对仓库根目录（`lhc-context-demo`）；行号对应冻结版 `157ba3a`。

**用户已经定的事**：
- 记忆改为分库调用，作为默认做法，不保留单次调用的对照。
- 同一个模型看同一张图可能犯同一种错，先从各调用的系统提示词入手解决。

本清单汇总了 Claude 和另一个 GPT 实例两轮只读讨论的结论。

**为什么要改**：现在每一步只有一次记忆调用，同时写四个库，一次看错就会同时写进几个库。0025 第 000000 次调用把一条电视柜认成"灰色台面"，同时写进了三个库：
- Task："候选工作区"；
- Object："值得靠近看看有没有刀"，标为 observation/supported；
- Spatial："砖柱旁的灰色台面"。

这三条又一起挑给了规划器。从第 000002 次调用（第 387 步）起，四个库里都出现了这个说法。规划器看到的像是几个独立来源互相印证，实际上是同一次判断抄了几遍。

另外，第 000000 次调用时 `decision` 还是 null，没有规划器的叙述。当时的任务目标写的是"approach its counter"（`lhc_demo/configs/search-trial-20-deepseek.json:2`），目标里的位置预设可能也起了作用。这一点还没有做因果验证。

**什么时候合入**：
- 1021 工具修复要求记忆部分保持不动，因为 R3 要和 V3 直接比较。所以本清单在 1021 的 R3 验收之后再合入；在那之前，可以先在分支上开发。
- 两边都会改到 `progress.py` 和 `tools.py`，合并时要注意：1021 的 F4 改运动统计，本清单改语义进展。

## 一、目标结构

每一步有四个模型调用，加一个由程序维护的 Task：

| 调用 | 看什么 | 不看什么 | 输出 |
|---|---|---|---|
| 判断 | 动作前后的画面、动作前冻结的检查条件（见第二节）、实测执行反馈 | 规划器的理由和预期原文、任何记忆库 | 逐条判定"满足／不满足／不确定"，附证据（图像编号、区域）。动作进展、子目标完成、找刀完成三项分开记 |
| Object | 当前和上一帧画面；中性的目标查询（只写"刀"）；Object 自己的记录；做身份比较时附上的历史图像 | 规划器的理由、其他库、判断结果、任何位置预设 | 先列可见特征，再写实例记录：类别、可见性、身份（同一个／新建／暂缓）、操作就绪状态 |
| Spatial | 画面、相机位姿和里程计；Spatial 自己的记录；身份比较用的历史图像 | 任务目标、规划器的理由、其他库、判断结果 | 区域和地标、房间类型（有标志性设施才定）、实际看清了哪些部分 |
| Experience | 相关操作的原始帧和原始工具反馈 | 规划器的理由、其他库、判断结果 | 分字段记录：情境、方法、执行效果、视觉变化、适用性假设；允许空更新 |
| Task（程序维护，不调用模型） | 规划器声明的子任务和冻结条件、判断调用的结果 | — | 目标条件、当前子任务、逐条件的判定历史 |

**几条规则**：
1. **并行和提交**：四个模型调用基于同一份冻结快照并行执行，全部返回后统一提交。重试不能重复写入。
2. **只写自己的库**：由代码强制。越界写入一律拒绝，并记进审计。九月的离线对照里，Spatial 调用就出现过越界写 Experience。
3. **判断结果只进 Task**：别的调用都不读它，否则一次误判又会复制进几个库。
4. **挑给规划器的条目**：
   - Object、Spatial、Experience 各挑本库的条目；程序过滤无效键、限制数量，空选择照样保留。
   - Task 的条目由程序按"当前目标、未解决条件、最新进展"生成。
5. **来源要标给规划器看**：每条记录带上调用编号、原始帧和采集时刻。同一帧画出的多份描述，只算一份证据。
6. **库与库之间**：只通过证据编号（图像编号、区域）关联，不共享实体键，也不共享文字描述。
7. **冲突**：
   - 代码只检查两类：已经明确绑定到同一对象或同一条件、在同一时刻出现的互斥取值；以及库内的自相矛盾。
   - 自由文本的跨库冲突留给规划器和人工审计，不自动裁决。
   - 没检测到冲突，也不等于可信度更高。
8. **失败隔离**：
   - 每个调用各自重试；失败时保留历史记录，并标成"本步不可用"。
   - 判断调用失败时，本步记为 `unassessed`。
   - Object 调用失败时，本步不放出任何操作目标，免得沿用旧的就绪状态。

## 二、检查条件：在动作前冻结

**现状**：`expected_outcome` 是自由文本（`lhc_demo/contracts.py:33`）；`next_check` 也是文本，而且 off 模式下 search_plan 可以省略（`lhc_demo/models.py:433`）。规划器的叙述和看错的类别，都可能从这里进入判断。

**要做**：规划器的决策里增加结构化的检查条件，每条包括：
- 条件编号；
- 范围：动作进展、子目标、找刀完成三者之一；
- 待检的区域或对象：图像编号加区域框；
- 可观测谓词：用固定的小词表，例如 `visible`、`not_visible`、`visibility_improved`、`region_reached`。具体词表由你定，写进文档。

**规则**：
- 条件里不能带类别预设。比如"砖柱后的台面变清楚"，要拆成"指定区域的可见程度改善"和"该区域物体的类别待确认"两条。
- 条件在执行前冻结。没有条件的步骤记为 `unassessed`；证据不足的条件记为 `uncertain`。

**改哪里**：`contracts.py` 的 `Decision`、`Assessment`、`ToolResult`；`tools.py` 的 `parse_decision`；规划器提示词里讲输出格式的部分。

## 三、系统提示词

每个调用一份，放在独立文件里，哈希记进 manifest。

**共用规则**：
1. **先列证据，再写记录。** 先列可见特征和前后变化，写明图像编号和区域；类别解释单独列。引用检查通过，不等于这条记录就是 `supported`。
2. **事实和推断分开。** 拆成独立的断言，每条断言只有一种依据。依据的类型要区分：图像、执行反馈、目标声明、继承的旧记录。Task 里另有判断结果这一类。
3. **证据模糊时写 `uncertain`。** 模糊不算支持。
4. **观察记录里不放行动建议**，例如"值得靠近看看"。Experience 可以保留带条件的方法假设。
5. **没看到不等于没有。** 负证据要写明图像、区域、遮挡情况和可辨程度；判断不了目标在画面里能不能辨认出来，就写未知。
6. **旧记录是"待复核的历史说法"**，要保留它原来的来源。现在看不到的东西，保留最后一次看到时的事实和原证据，只更新"当前是否可见"。跨视角比较身份时，必须附上历史图像。
7. **没有尺度依据时不写尺寸**，比如"约半米高"。

**各调用的重点**：
- **判断**：只按冻结的条件逐条回答。动作完成、画面变化、子目标达成分开记；家具变大、视角变化都不算进展。
- **Object**：
  - 先写形状、材质和部件，再给类别。
  - 只有确实有歧义时，才列备选类别和区分它们的特征；不要硬凑第二个类别。
  - "厨房台面"这类功能类别，需要额外特征支持，比如水槽、灶台。
  - 身份只能在"同一个、新建、暂缓"三者中选，拿不准就暂缓；互相冲突的候选分别保留。
- **Spatial**：
  - 只描述位置关系、遮挡和能辨认的细节；检查范围限定在实际看到的表面。
  - 没有标志性设施时，房间类型写未知。
  - 不能从转过的角度累加推出"已经搜完"。
- **Experience**：
  - 执行效果只能用工具反馈来支持，比如停止原因、运动估计。
  - "因为某个东西挡住了"这类说法需要视觉证据。
  - 单个案例只算带情境的假设。

**提示词解决不了的**：同一个模型看同一张图，仍可能犯同一种错，比如几个调用都把电视柜当成台面；被遮挡的东西也补不出来。这类疑点最终要靠近景、换视角或其他机载证据来解决。证据分流放到下一步再做，不在本清单里。

## 四、按文件的修改

| 文件 | 要改什么 |
|---|---|
| `lhc_demo/models.py`（`LLMMemoryManager.__init__`、`assess`，454 行附近） | 建四个独立客户端：判断、Object、Spatial、Experience，各配专用提示词和输出格式，代码强制写入权限。各自重试，失败按第一节第 8 条处理。规划器提示词的输出格式加上冻结条件，并说明来源字段的含义 |
| `lhc_demo/models.py`（`ChatClient.request`，269 行附近） | 审计改成带版本的格式，用 `batch_id`、`call_id`、`role`、`attempt` 把调用和观测、决策对应起来。每次调用保存：实际输入、图像哈希、原始输出和解析结果、被拒的更新及原因、提交前后的版本号、选择结果、耗时、token。格式修复记在原调用名下；规划器用同一套编号 |
| `lhc_demo/context.py`（`memory_input`、`apply`、`apply_proposal`、`packet`、`interaction_targets`） | 按调用分别组装输入：现在的输入包含全部库、进度摘要和 Spatial 派生的内容（`context.py:96`），历史反馈里还带着规划器的理由（`context.py:340`），这些都要去掉。另外四件事：逐库提交，给每条记录加上有类型的来源；同帧的证据去重后再呈现给规划器；Task 改由程序更新；`interaction_targets` 继续从 Object 的当前记录派生，补上观测编号、采集时刻和冲突检查 |
| `lhc_demo/contracts.py`、`lhc_demo/tools.py` | `Decision` 加冻结条件；`Assessment` 改成逐条件判定，动作进展、子目标完成、找刀完成三项分开；`ToolResult` 记录各调用的状态 |
| `lhc_demo/runner.py`（`assess`、`run`） | 基于冻结快照并行调用，统一提交；写审计事件。Task 的程序更新单独记成事件，不能伪装成一次模型调用 |
| `lhc_demo/progress.py` | 依赖判断的计数，比如 `consecutive_calls_without_confirmed_progress`，改读判断调用分开给出的进展状态。运动统计按 1021 的 F4 处理 |
| `lhc_demo/session.py`、`lhc_demo/runtime_update.py` | 默认配置为四路调用，每路可设输出预算、超时、重试和并发上限；提示词哈希记进 manifest。旧的 `observer`、`memory_manager` 配置映射到新默认；不提供切回单次调用的开关 |
| `analysis/` 下的回放脚本，以及后面检查器界面的读取层 | 读新格式。旧运行按 `legacy_unified` 读取；恢复不出来源的标"未确认"，不能编造出四份独立来源。旧记录里的操作就绪状态，要重新观测确认后才能用 |

**需要用户先确认的一项**：把任务目标改成中性的写法，例如"找到刀，并让它在头部相机里清楚可见"，所有目标里都去掉"its counter"这类位置预设。用户确认之前不改。

## 五、测试

- **`tests/test_memory_manager.py`**：
  - 输入隔离：每个调用看不到其他库、规划器的理由和判断结果；
  - 越界写入被拒；
  - 没有呈现过的证据和未来的证据不能被引用；
  - 并行返回顺序打乱；
  - 超时和重试不会重复写入。
- **`tests/test_task_planning.py`**：
  - 条件在执行前冻结，执行后不能改；
  - 进展和完成分开判；
  - 条件缺失时记为 `unassessed`。
- **`tests/test_interaction_grounding.py`**：
  - 旧帧和 scan 中途的早期帧不能放出操作目标；
  - Object 记录有冲突，或 Object 调用失败时，不放出操作目标。
- **审计读取**：
  - 能按调用还原每一步；
  - 能读旧格式；
  - Task 的程序更新事件能重放。
- **来源和旧事实**：
  - 来源类型正确；
  - 现在看不到的旧事实仍然保留。

## 六、验收

- **离线**：用 0021–0026 等已有轨迹的原始输入，重放新结构；不执行动作。对人工标注的决策点报告：
  - 判断的误报、漏报和"不确定"的比例；
  - 同一个错误出现在几个库里；
  - 身份误合并；
  - 错误的操作目标被放出；
  - 成本，包括 token 和延迟，并和九月离线对照的 4.24 倍比较。
- **重点核对 0025 的电视柜**：新结构下，有没有哪个库把它记成"台面"或"候选工作区"；有的话，出现在几个库里。
- **在线**：在 1021 修好的工具版本上，从实例 0 跑 3 轮，报告同上的指标，再加上找刀的进展。不要求找到刀。

## 七、不在本轮范围

- 运行检查器界面：设计稿另给，说明随后单独写。本清单只要求审计格式能支持它。
- 证据分流：比如 Object 看局部放大的画面、判断调用看动作前后的对比图。放到下一步。
- 单次调用的对照：用户已决定不保留。
