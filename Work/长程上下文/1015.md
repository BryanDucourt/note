## 结论

核对对象：GPT 关于“统一记忆＋按消费者压缩”的调研，共九篇。九篇都对照了 Zotero 里的全文，LatentMem 另看了公开代码（commit `4872806`）。

**逐篇描述基本属实**，没有发现编造的机制或数字。**问题出在推断上：**

1. **“已有工作直接覆盖这一组合”说过头了。** GPT 自己把消费者定义为规划器、动作策略、状态判断器，但最接近的 LatentMem 和 G-Memory 不是这种设定：
   - 消费者是同一个 LLM 底座上的不同角色 agent；
   - 记忆来源是过去任务的轨迹，不是当前任务的上下文；
   - 记忆按角色在任务开始时定一次，不随当前这一步变化。

   九篇里，真正在当前任务内、每轮按消费者供给的只有 RCR-Router；消费者真正异构的只有 HiMe，但它的分配是人工固定的。
2. **漏了两条对我们最关键的证据。**
   - LatentMem 去掉角色条件的消融，本身就是“同预算下共享压缩 vs 按角色压缩”的对比。
   - RECOMP 的跨模型迁移实验说明：消费者相近时，同一份压缩部分可以通用，但有损失。
3. **漏了“错误连带”。** LatentMem 在动机里提到同质记忆会放大相关错误，但九篇都没有实验测量。这是之前讨论过的方向，目前仍然空着。
4. **第三个候选问题（摊销多消费者的压缩成本）已被 FocusMem 的结构部分覆盖**：共享编码器，按记忆用途设内容基，再按当前决策状态读出。
5. 关于 LHC“四库独立、共享原始证据”的判断，是对我们自己系统的设计判断，论文里核对不了。

## 逐篇核对

### LatentMem

arXiv 2602.03036v2。[论文](https://arxiv.org/abs/2602.03036) · [代码](https://github.com/KANABOON1/LatentMem)

**属实**：
- 经验库只存原始轨迹，不做摘要或 insight 提取（§4.2）。
- 记忆生成器以角色画像和检索到的轨迹为输入，输出定长 latent 记忆（式 5）；用 LMPO 以任务奖励训练，agent 底座冻结（§4.4）；latent 长度 $L'=8$（§5.1）。
- 去掉角色条件后，AutoGen／KodCode 降 2.30 个点，MacNet／KodCode 降 6.45 个点，复杂协作结构降得更多（§5.6）。
- 代码里 `retrieve_memory()` → `_construct_latent_memory()` 确实传入任务描述、文本记忆、角色，以及该角色在检索轨迹里的发言；有 latent 记忆时，文本记忆被置空，agent 只用 latent（`agent.py` 的 `_trigger_memory`）。

**需要补充的边界**：
- 存的是过去任务的轨迹，而且 $K=1$，每个任务只取 1 条最相似的历史轨迹（§5.1）。
- 式 5 的输入只有角色和检索轨迹，不含当前这一步的输入；代码里也是按任务描述触发。所以同一任务里同一角色拿到的记忆是固定的：按“角色”定制，不按“当前要做的决定”定制。
- latent 要拼进 agent 的隐状态，生成器从 agent 底座初始化，要求消费者是同一族开源模型、能白盒注入。VLA、闭源 VLM 这类异构消费者用不了这套接口。
- 角色消融只报了 KodCode 上两个框架的数字，没有误差范围。
- 动机里写“同质记忆……放大相关错误”（引 Cemri et al., 2025），但没有相应实验。

### G-Memory

arXiv 2506.07398v2。[论文](https://arxiv.org/abs/2506.07398)

**属实**：
- insight、query、interaction 三层图。先在 query 图上检索并做 1 跳扩展，再向上取 insight、向下取稀疏化后的交互子图（§4.1–4.2）。
- 式 8 以 $\mathrm{Role}_i$ 和 $Q$ 为条件给每个 agent 装记忆；附录 C 的提示词是让 LLM 把通用 insight 改写成针对某个角色的 insight。
- 实现里在任务开始时调用一次，更细粒度的调用是作者建议的可选配置（§4.2）。

**补充**：
- 同样是跨任务经验。
- 消融只拆了 insight 和交互两个组件，没有“去掉角色定制”的消融。角色定制的收益是作者的归因（§5.2 Takeaway 2），没有直接证据。
- 基准里有 ALFWorld、SciWorld 两个文本具身环境。

### RCR-Router

arXiv 2508.04903v4，2026-10-12 更新。[论文](https://arxiv.org/abs/2508.04903)

**属实**：
- 从共享记忆中按角色、任务阶段和预算选条目，目标是相关性加和（§3.1 式 2）。
- 预算分配器用策略梯度学（式 3–4）；重要性打分器用日志轨迹做弱监督学习（§3.2.2）。
- 每轮把 agent 输出抽成原子记录写回共享记忆（§3.3 IRF）。
- 所有对照方法共用同一套原子记忆、序列化和去重规则，只有路由策略不同（§3.3 “Memory control”）。
- ALFWorld 设 Planner、Navigator、Interactor、Verifier 四个角色（附录 F.3）。

**补充**：
- 原子记录由一个统一的 Memory Update Agent 生成，相当于“压缩一次、大家共用，再按角色挑选”，不针对角色改写内容。
- 消费者都是黑盒文本 LLM。
- 九篇里只有它在当前任务内、每轮为不同角色供给，和我们的设定最接近。
- GPT 说“加和目标刻画不了需要组合起来才有用的证据”，这个批评成立。

### MemCompiler

本地是 v2，GPT 引的是 v1。[论文](https://arxiv.org/abs/2605.07594)

**属实**：表 5 的数字和 v2 一致。执行器输入从 2481.1 降到 1003.2 tokens，编译器另用 2081.4 tokens；延迟方面，编译器 0.093s 加执行器 0.12s，低于原执行器的 0.30s。

**补充**：按表中数字把三项 token 相加，新方案约 3093（1003.2＋8.2＋2081.4），原方案约 2499（2481.1＋18.2），总量反而多了约 24%。“更省”只在延迟这个口径下成立。

### GAM

arXiv 2511.18423v1。[论文](https://arxiv.org/abs/2511.18423)

**属实**：Memorizer 生成轻量 memo，并把完整历史按页存进 page-store；Researcher 按客户端请求反复检索、反思，生成定制上下文（§2.2）。评测是 LoCoMo、HotpotQA、RULER、NarrativeQA（§3.1）。

**补充**：只有一个客户端，定制的依据是请求文本，不涉及多个消费者。它对我们的价值在“统一存储完整历史，用到时再生成上下文”这一半，可以作为统一存储设计的先例。

### RECOMP

arXiv 2310.04408v1。[论文](https://arxiv.org/abs/2310.04408)

**属实**：有抽取式（对比学习）和生成式（从大模型蒸馏）两种压缩器，都用目标 LM 在下游任务上的表现构造训练信号；文档没用时输出空摘要（§2–3）。

**GPT 漏掉的关键结果**：跨模型迁移（p.8，Table 1 与附录 Table 10）。
- 语言建模：为 GPT-2 训练的压缩器迁到 GPT2-XL、GPT-J，效果依然好。
- 开放域问答：为 Flan-UL2 训练的压缩器迁到 LLaMA-13B，表现变差，和 LLaMA 自己的 oracle 压缩差距明显。

这是“压缩要不要按消费者定制”较早的直接证据：任务相同、消费者相近时，共享的压缩部分可用，但有损失。

### HiMe

arXiv 2607.03449v1，之前已对照论文和代码 `261766e` 核过。[论文](https://arxiv.org/abs/2607.03449)

**属实**：Executor 只用当前观测和子目标，Sentry 用近期窗口，Planner 管理长期多模态记忆和计划表；低层依赖“给定子目标后可以忽略长期历史”的假设（§3.3）。

**补充**：
- “已有实机结果”没错，但证据薄：每格 20 次，只和自己搭的变体比。
- 主动管理比“全部保留”只高 4 个点（86 → 90）。
- Sentry 在 8 帧时召回率只有约 35%。

### MAGMA

本地 arXiv 2601.03236v2。[论文](https://arxiv.org/abs/2601.03236)

**属实**：每条记忆同时进语义、时间、因果、实体四张图；按查询意图路由、选择遍历方式（§3.1–3.3）。评测是 LoCoMo、LongMemEval。

**补充**：只有一个消费者（问答），视图按查询类型切换。对我们是“同一来源、多种组织视图”的先例。

### FocusMem

arXiv 2608.04530v1。[论文](https://arxiv.org/abs/2608.04530)

**属实**：把三件事分开建模：内容（按记忆用途设内容基）、读出（按当前决策状态读出）、信任（门控，决定这段记忆是否进入策略）。这里的 role 指 episodic 和 working 两种记忆用途，不是不同的消费者；GUI 策略冻结；评测是五个 GUI 基准。

**补充**：
- working memory 来自当前任务中已经滑出窗口的那段历史（§3.1）。也就是说，它已经在做“当前任务的历史 + 按当前决策状态读出”。
- episodic 和 working 两类记忆共用编码器和压缩器（§3.3）。所以 GPT 第三个候选问题“共用一次证据编码，再按需读出”，在单消费者情形下已经有现成结构；要做的话，新意只能落在多个异构消费者上。

## 对方向判断的影响

**宽泛说法确实站不住。** 在文本多智能体里，“共享来源＋按角色定制记忆”已有 LatentMem、G-Memory、RCR-Router。LatentMem 的消融还给出了初步证据：同预算下，按角色压缩比共享一份好，协作越复杂越明显。

**就这九篇而言，仍然空着的：**

1. **异构消费者**：输入模态、调用频率、接口都不同，比如 VLM 规划器、VLA、监控器。九篇里只有 HiMe 有异构消费者，但分配是人工固定的。
2. **面向多个消费者、按当前决策（不只是按角色）压缩**：FocusMem 做了按决策状态读出，但只有一个消费者；RCR 按阶段选择，但不改写内容。
3. **错误连带**：没有一篇测过共享摘要出错后，错误如何在消费者之间传播。
4. **证据更新后，派生视图的同步**：九篇都有写回或更新机制，但都没有处理“已经发给各个消费者的摘要，怎样随证据变化失效和更新”。

**GPT 的三个候选问题：**

- **多消费者需求冲突时的联合压缩**：方向对，但要有异构消费者才有意思，否则只是 LatentMem、RCR 的延伸。
- **证据更新后的同步**：九篇里覆盖最少的一块，值得保留。
- **摊销多消费者成本**：FocusMem 已有“共享编码＋按需读出”的结构，单独做偏弱。
- 建议补上第四条：**错误连带**。

**阅读顺序**：同意先读 LatentMem 和 RCR-Router；建议把 FocusMem 提到 G-Memory 前面，因为它的“按决策状态读出”和我们最相关；RECOMP 只看跨模型迁移那一节。
