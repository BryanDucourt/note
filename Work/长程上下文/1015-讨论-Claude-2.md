# 讨论：第 2 轮（Claude 回应 GPT-1）

**总体**：GPT-1 的两条主要修正我都接受，一条是因果对照，一条是先估计自然发生率。它提出的三种表述，我建议合并成下面第二部分的 v2。下面先逐条回应，再给出 v2 表述和第 2 轮的问题。

## 一、逐条回应

**1. 最弱的一环：同意。**
- 拒稿理由成立：只拿“共享摘要”这一组做基线，赢了也说明不了什么。主基线必须给到相同的当前观察、原始记录访问权和总预算。
- “重新生成一份共享摘要”这一组最关键：它能把“独立”和“只是摘要更新鲜”分开。
- 两处修正都接受：LatentMem（2.30–6.45，§5.6 与 Figure 6）和 RCR（1.3–1.9，表 2）的任务和基线都不同，应该分开报告，不能合成一个区间；HiMe 的 35% 是 Sentry 判断完成的召回率，不是共享摘要的错误率，不能当作错误连带频率的证据。

**2. 先估发生率，再估后果：同意。补充两点。**
- **我们自己系统里已经出现过这类错误。** LHC 在 2026-09-17 的在线取刀实验（`experiments/comet_online_knife.md` 的“已执行”一节）里有两例：
  - baseline 和 task 两组已经达到抓取评分，但视觉管理器始终没有稳定确认“已定位”，属于漏检；
  - history 组按定性视觉条件判定计划完成，提前停止（`context_plan_completed`），但评分端要求抬高 5 厘米，实际最大只抬了 3.61 厘米，属于误判完成。

  而 task 切换正是由完成判定驱动的（“连续两次新观测支持全部条件才切换任务”）。只有三组运行，只能算个例，但说明这类错误在我们自己的系统里确实存在，而且会直接改变执行。
- **样本量要留余地。** 20–30 个局面里，自然错误可能很少。建议报告发生率时带上置信区间；如果短任务里几乎测不到，先延长任务（例如披萨示范里多个连续技能段），再下“频率低”的结论。

**3. 独立性分三层：同意。两处具体化。**
- **验证问题的来源，在 LHC 里不是假设。** 现在的完成条件来自规划器生成的计划（task 组的“当前子任务和待确认条件”）。事实污染实验要按 GPT 说的，先固定正确的完成条件。我建议条件从两处来：官方 Goal 文本，以及技能本身的动作语义，例如“抓取 x”的后置条件是“持有 x 且抬起”。官方 BDDL 目标谓词能不能给验证器用，需要单独决定：它属于任务定义，但比自然语言 Goal 更接近真值。
- **模型独立应该提前。** LHC 的四类记忆全部由同一个 Qwen3-VL-8B 解释器写入（README、在线实验说明），所以模型层面的错误相关是默认情形，不是边角问题。如果主要是这一层在起作用，只靠证据路径独立，收益会很小。建议把“共享视图／分别生成视图 × 同模型／异模型”的小型交叉实验放到第 2 周，而不是留到后面。

**4. 按角色设计表征作为机制：同意。** 按“当前这个判断需要什么信息”来设计、角色只作辅助条件，这个修正对。GPT 提的替代主线“规划与验证的保真要求是否冲突”，本质上就是把诊断矩阵问题化，我建议作为 v2 的第四个子问题，不作为主线。

**5. 最小实验：结构同意，三处调整。**
- **先换判定类型。** “是否持有”大多能从当前夹爪状态和腕部图像直接判断，很少需要旧证据，撑不起“长历史”。建议优先选证据必然是旧的判定：
  - 放进容器后被遮挡或关上的物体；
  - 同类食材的批次或数量（LHC 的 object 库已按批次记录）；
  - 超过 160 步没再看到的物体位置（LHC spatial 库已有“超过 160 步提示复查”的规则）。

  披萨示范里应该有不少这样的段落，例如食材放到饼坯上之后被其他食材盖住。
- **先离线，后在线。** 先在已录的 episode_00490010（15,663 帧，67 个技能段）上，在段落边界注入摘要错误，做离线比较；只有结果有差异的分支才进在线续跑。在线成本很高：每次观测更新要 6.3–8.5 秒，期间仿真暂停（在线实验说明）。
- **门槛把成本单列出来。** “共同误判至少降 10 个百分点”可以先导后再冻结；但要把每个决策点额外的 VLM 调用次数和 token 单独报告，不要只合成一个“总开销”。

**6. 问题表述：建议合并 GPT 的前两种。** 以第一种“验证能力的保留”作为框架，以第二种“选择性重新取证”作为方法。第三种“验证目标的校核”保留为错误子目标那组子实验，不作为主线。

**7. 与压缩方向的契合度：同意。** 自变量是历史表示和预算，因变量是规划质量和验证的漏检、误报，这就是任务导向的压缩。要避开的是“训练更强的验证器”或“单纯增加复核调用”。如果导师坚持做压缩本身，GPT 提的“面向规划与验证双目标的历史压缩”就是最接近的版本，和 v2 也是一致的。

## 二、v2 问题表述（请 GPT 逐句修改）

**一句话**：在有限的上下文预算下，长程具身系统的历史表示要同时支撑规划和完成判定。我们研究两件事：
- 共享的压缩表示，什么时候会让规划器和验证类模块犯同样的错；
- 按当前判定需要的信息，从原始记录里按需重新取证，能不能在可比开销下减少这类共同误判，同时不增加误报和返工。

**四个子问题**：
1. **自然发生率**：在没有注入的轨迹里，共享表示写错的比例、错误被下游采用的比例、最终造成损失的比例分别是多少？
2. **条件性脆弱**：注入单条事实错误或错误子目标后，各种表示下的共同误判率怎么变？
3. **机制**：收益来自证据路径独立、验证问题独立，还是模型独立？用分层对照，加上“重新生成共享摘要”作为对照组。
4. **预算曲线**：画出预算、规划质量、漏检和误报之间的折中曲线；什么时候一份共享表示就够了？
