## 讨论用摘要

**总体结论**：“按角色定制记忆”已有 LatentMem、RCR-Router，“为验证挑选事件证据”已有 REFLECT；但四篇都没有测量过共享摘要出错后，错误怎样在模块之间传播。建议把主线收到“错误连带＋独立的验证视图”上，证据选择只作为实现机制。

**LatentMem**
- 共享的过去轨迹库 → 按角色生成 8 个 latent token，用任务奖励训练；同预算下去掉角色条件，KodCode 上降 2.30–6.45 个点。
- 存的是过去任务的经验；记忆只取决于任务和角色，不随当前这一步变化；消费者必须是同族、可白盒注入的 LLM，VLA 用不了。
- 代码 README 写着训练前先做 SFT 冷启动，论文没提；代码还只检索成功的轨迹。

**RCR-Router**
- 在当前任务内，每一轮按角色、阶段、预算从共享记录里给每个 agent 选一个子集；ALFWorld 成功率 59.1 → 67.3，token 6.82K → 4.30K。
- 只选择、不改写；消费者是黑盒文本 LLM；只按角色路由比共享检索只高 1.3–1.9 个点。
- ALFWorld 设了 Verifier 角色，但没有单独评估它；v4 是 10 月 12 日的大改版，没有代码。

**REFLECT**
- 多感官观测 → 场景图 → 事件关键帧 → 子目标末帧，三层摘要；先逐个子目标验证，失败了再调细节解释。
- 和我们“为验证挑证据”最接近，但它是执行结束后的离线分析、没有预算、只用一个 LLM；数据集里只有失败案例，测不了误报。
- “先让 LLM 写一份通用摘要”的消融明显更差（仿真 Exp 55.8 vs 88.4），可以作为“共享摘要会丢失验证所需信息”的旁证。

**HiMe**
- 三层异构消费者（大 VLM、小 VLM、VLA），上下文由人工固定分配；ICML 2026 poster。
- Sentry 只看最近 8 帧，召回约 35%；它读的是 Planner 写的计划表，结构上天然存在错误连带。
- 证据薄：每格 20 次，基线都是自己搭的；论文与代码有 5 处不一致，复现要以代码为准。

**讨论问题**
1. 主线定为“错误连带＋独立验证视图”、证据选择作为机制，是否认可？
2. REFLECT 已有事件关键帧和逐子目标验证。“在线、限预算、多个消费者”作为增量，够不够？
3. 测试平台先用 HiMe 的真机三层系统，还是 BEHAVIOR 这类有真值的仿真？
4. 先只做 VLM 类消费者（规划器、监控、评估），VLA 放到后面，可以吗？
5. 压缩器一开始就要训练（LatentMem、RCR 都训了），还是先用规则和提示词把现象做出来？

## 一、LatentMem

### 1. 基本信息

- arXiv 2602.03036v2（2026-03-09），预印本。
- 作者单位：同济、上海 AI Lab、港中文、南京大学、上海交大（v2 作者列表）。第一作者 Muxin Fu 也是 G-Memory（NeurIPS 2025）的共同一作。
- 代码：[github.com/KANABOON1/LatentMem](https://github.com/KANABOON1/LatentMem)，核对的是 commit `4872806`；Hugging Face 上有训练好的模型。

### 2. 一句话和要解决的问题

**一句话**：用一个可训练的记忆生成器，把检索到的过往多智能体轨迹和当前 agent 的角色描述一起，压成 8 个 latent token，拼进这个 agent 的输入；生成器用任务奖励训练（LMPO）。

**问题**：作者认为现有多智能体记忆有两个毛病（§1）：
- **记忆同质化**：所有 agent 拿到一样的记忆，忽视角色差异，削弱角色遵循，并且“放大相关错误”；
- **信息过载**：多粒度的记忆条目太多，淹没了关键信号。

### 3. 方法

| 维度 | LatentMem |
| --- | --- |
| 存储来源 | 过去任务的原始轨迹，每一步记录活跃 agent、输入、输出，不做摘要或 insight 提取（§4.2）。经验库用训练集上跑出的 40,580 条轨迹初始化（附录 B.4.2），每个任务结束后追加新轨迹（式 4）。按任务相似度取 top-K，主实验 K=1（§5.1）。 |
| 消费者 | 同一个多智能体系统里的不同角色：AutoGen 2 个，MacNet 5 个（含 edge agent），CAMEL 4 个，DyLAN 4 个加 1 个 ranker（附录 B.3）。【推断】同一系统内各 agent 用同一个 LLM（§5.1 只给出两种底座），属于同构消费者。 |
| 定制依据 | 角色画像 $\gamma$ 和检索到的轨迹（式 5）。式 5 的输入里没有当前这一步的输入 $p_j$，代码里也是按任务描述触发（见第 6 部分），所以同一任务中同一角色拿到的记忆不随步骤变化。 |
| 压缩方式 | 生成固定长度的 latent 记忆，$L'=8$（§5.1），拼到 agent 隐状态序列的后面（式 6）。生成器从底座 LLM 初始化，用 LoRA（r=16）训练（附录 B.4.3、表 3）。 |
| 训练信号 | LMPO：GRPO 的变体，用组内相对优势、token 级目标（式 9–13）；agent 底座冻结，只训练生成器（§4.4）。 |
| 更新与一致性 | 只追加，不删改（式 4），没有失效机制。 |
| 验证 | 没有专门的验证模块。部分框架里有 critic、test agent 之类的角色，但它们只是普通消费者。 |
| 共享 vs 分开 | 有。“w/o role”消融去掉角色画像，所有 agent 拿到相同的 8 个 latent token：KodCode 上 AutoGen 降 2.30，MacNet 降 6.45（§5.6，Figure 6 右）。 |
| 错误传播 | 只在动机里提到同质记忆“放大相关错误”（§1，引 Cemri et al., 2025），没有测量；§5.7 的案例分析（Figure 7）是定性的。 |
| 成本 | 报了总 token 和总时间（Figure 3、Figure 8）。AutoGen＋KodCode 总 token 1.76e6，无记忆是 1.77e6；MacNet＋TriviaQA 是 1.98e7，无记忆是 9.70e6。DyLAN＋TriviaQA 总时间 3.15e4 s，无记忆是 2.17e4 s。生成器的训练成本没有报告。 |

### 4. 实验

- **数据**：六个基准。TriviaQA、KodCode、StrategyQA、PopQA 是训练域；BigCodeBench、PDDL 是域外。AutoGen、MacNet 参与训练；CAMEL、DyLAN 是没见过的框架（附录 B.4.1）。
- **底座**：Qwen3-4B-Instruct-2507（表 1）和 Llama-3.1-8B-Instruct（表 4）。
- **基线**：Voyager、Generative、JoyAgent（单智能体记忆，改造成多智能体），MetaGPT、ChatDev、OAgents、G-Memory（附录 B.2），都在同一框架里实现；非参数基线把同样的 40,580 条轨迹存进各自的记忆（附录 B.4.2）。另外和多智能体微调方法 MARTI 在同等算力下比较（§5.4、表 2）。
- **样本量与方差**：测试集规模论文没写（未核实）；评测温度 0（表 3）；没有报告多次运行的方差。
- **关键数字**（表 1，Qwen3-4B，六个基准平均）：

  | 框架 | 无记忆 | G-Memory | LatentMem |
  | --- | --- | --- | --- |
  | AutoGen | 53.61 | 56.09 | 62.75 |
  | MacNet | 50.73 | 57.21 | 60.02 |
  | CAMEL（未见过） | 53.22 | — | 61.12 |
  | DyLAN（未见过） | 51.51 | 56.15 | 60.72 |

  域外的提升：BigCodeBench 1.56–3.34 个点，PDDL 4.40–7.10 个点（表 1）。
- **做了的消融**：w/o role、w/o experience update（§5.6）；$L'$ 和 K 的敏感性（Figure 6 左、附录 C.3）。
- 【推断】**没做的对照**：把 latent 换成等长文本摘要，用来区分“latent 形式”和“角色定制”各自的贡献；多次运行的方差；记忆随当前状态逐步更新的变体。
- 【推断】训练域上提升大（四个框架里 TriviaQA、KodCode 的提升在 7.05–16.20 个点之间），域外 BigCodeBench 只有 1.56–3.34。这和“只有它在训练数据上做了参数训练”是一致的。

### 6. 论文与代码是否一致（commit `4872806`）

1. **角色进入生成器**：一致。`latentmem/mas_core/memory/latentmem.py:77` 的 `retrieve_memory()` 调用 `:143` 的 `_construct_latent_memory()`，把任务描述、文本记忆、角色，以及这个角色在检索轨迹里的发言拼成提示词交给生成器。最后这一项“该角色的历史发言”论文式 5 没有写。
2. **只用 latent**：一致。`latentmem/utils/agent.py:341` 的 `_trigger_memory()` 在有 latent 记忆时，把文本记忆置空（:352）。
3. **检索**：基本一致，有一处细节。`configs/latentmem/kodcode.yaml` 用 metagpt 模式，`pos_shots_num: 1`、`neg_shots_num: 0`、`latents_len: 8`，对应 K=1、$L'=8$。但 `latentmem/mas_core/memory/backbone/metagpt.py:49` 检索时加了 `filter={'label': True}`，只取成功的轨迹，论文式 3 没提。
4. **训练流程**：不一致。`README.md:52` 写的是先做 SFT 冷启动再跑 LMPO（`scripts/sft.sh`），论文 §4.4 和附录 B.4 只描述了 LMPO。

## 二、RCR-Router

### 1. 基本信息

- arXiv 2508.04903v4（2026-10-12；v1–v3 都在 2025 年 8 月），预印本。
- v4 的 PDF 标题已经改为 “Role-Conditioned Context Routing for Resource-Efficient Multi-Agent LLM Systems”，arXiv 页面上还是旧标题。
- 作者来自 CMU、Northeastern、Harvard、MIT 等，共 16 位。
- 正文里留有回复审稿的措辞：“as suggested by the reviewer”（附录 B.2）、“We will add this breakdown to the revised paper”（§4.9）。
- 论文没有给出代码链接。

### 2. 一句话和要解决的问题

**一句话**：不改多智能体的拓扑，每一轮按 agent 的角色、任务阶段和预算，从共享记忆里给它挑一个子集；预算和相关性打分都是学出来的；agent 的输出再整理成原子记录，写回共享记忆。

**问题**：现有多智能体框架大多全量共享上下文，或者用固定模板，多个 agent 反复处理重叠的、和自己角色无关的内容，浪费 token 和时间，还可能干扰推理（§1）。

### 3. 方法

| 维度 | RCR-Router |
| --- | --- |
| 存储来源 | 当前任务内的共享记忆 $M_t$：agent 交互历史、检索到的文档和工具输出、实体和子计划等结构化状态（§3.1）。每轮由 Memory Update Agent 把 agent 输出抽成原子记录 `{role_tag, stage_tag, timestamp, content}` 写回（§3.3、附录 E）。ALFWorld 平均每个任务 24.3 条、4.1K token（附录表 10）。 |
| 消费者 | 黑盒文本 LLM agent（主实验用 GPT-5-mini，§4.1），同构。HotPotQA 3 个角色；ALFWorld 4 个：Planner、Navigator、Interactor、Verifier；WebShop 4 个（附录 B.7、F.3）。 |
| 定制依据 | 角色 $R_i$、任务阶段 $S_t$、预算 $B_i$，每轮一次（式 2）。阶段是框架给的元数据，而且是可选的，不是从当前状态推断出来的（附录 B.7、C）。 |
| 压缩方式 | 只选择，不改写：按 α/ℓ 贪心挑条目，再和“单条最优”比较，取较好的那个（式 2、算法 1）。预算从 {512, 1024, 2048, 4096} 中选（式 3）。 |
| 训练信号 | 相关性打分器：用日志轨迹的弱标签做二分类（§3.2.2、附录 D）。预算分配器：策略梯度，奖励是任务指标减去 token 和延迟惩罚（式 4、附录 B.3）。agent 本身不训练。 |
| 更新与一致性 | 每轮写回；同角色、同阶段内去重；冲突时保留较新的条目（§3.3、附录 E）。作者说明不假设语义冲突能完全解决。已经发出去的上下文不会失效。 |
| 验证 | ALFWorld 的 Verifier 和其他角色一样，拿到路由后的上下文；它看到的是由 agent 输出整理成的文本记录，不是原始观测（附录 F.3）。没有单独评估 Verifier。 |
| 共享 vs 分开 | 有。附录 B.2、B.4 说，检索类基线在同一记忆池、同一预算下“检索一份共享上下文”；表 2 还有只用角色、只用阶段、固定预算等变体。 |
| 错误传播 | 没有测量。§4.8 在 HotPotQA 的中间步骤注入失败，但只统计重试带来的 token 和时间增长（表 5）。 |
| 成本 | 每个任务的 token 和运行时间，取 5 次运行的均值（表 1）；路由本身占运行时间的 2.2%（表 6）。Memory Update Agent 的开销没有单列，论文没说明是否计入。 |

### 4. 实验

- **数据**：HotPotQA（测试 7,405）、ALFWorld（测试 134）、WebShop（测试 500）（附录表 10）；附录 G 另有 MuSiQue、2WikiMultihop。
- **基线**：Full-Context、Static Routing、Self-RAG、End-to-End Beam Retrieval、Multi-Agent Debate（§4.1），在统一设置下实现；表 8 还比较了 MMR、学习式重排和通用 prompt 压缩。
- **样本量**：5 次独立运行，报均值±标准差（表 1）。
- **关键数字**（表 1）：

  | 基准 | Full-Context | RCR |
  | --- | --- | --- |
  | ALFWorld 成功率 | 59.1 | 67.3 |
  | ALFWorld token | 6.82K | 4.30K |
  | ALFWorld 时间 | 145.3s | 94.5s |
  | HotPotQA F1 | 74.6 | 83.6 |
  | WebShop 奖励 | 0.565 | 0.653 |

- **受控对比**（表 2，ALFWorld 成功率）：语义检索 64.0，只用角色 65.9，只用阶段 65.2，固定预算 66.3，RCR 67.3。
- **通用 prompt 压缩**（表 8，ALFWorld）：token 更少（3.75K vs 4.30K），成功率 65.8 vs 67.3。
- **其他**：模块消融（表 7）、IRF 轮数（表 3、表 4）、agent 数量（§4.7）、角色粒度（表 9）。
- 【推断】**没做的**：Verifier 的判断准确率；只有系统级结果，没有拆开看各个角色自己的表现变化；更长的任务。ALFWorld 上 Full-Context 才 6.82K token，压缩前的上下文本来就不长。

### 5. 结论站不站得住

| 结论 | 证据强度 | 依据 |
| --- | --- | --- |
| 在三个基准上改善了 token、时间与任务表现的取舍 | 支持 | 5 次运行、有标准差，在统一设置下和多个基线比较（表 1、表 2、表 8）。 |
| 按角色路由优于共享检索 | 弱 | 表 2 中只用角色比语义检索高 1.3–1.9 个点（HotPotQA 79.2 → 80.5，ALFWorld 64.0 → 65.9），差距不大；共享检索的具体实现，正文描述有限。 |

## 三、REFLECT

### 1. 基本信息

- CoRL 2023；arXiv 2306.15724v4。
- 作者：哥伦比亚大学的 Zeyi Liu、Arpit Bahety、Shuran Song。
- 项目页：robot-reflect.github.io。代码不在这次的核对范围内。

### 2. 一句话和要解决的问题

**一句话**：把机器人执行完之后的多感官数据（RGB-D、声音、本体状态）整理成三层摘要；先用最粗的一层逐个子目标检查有没有完成，发现失败后再调出更细的事件记录让 LLM 解释原因，最后据此生成纠正计划。

**问题**：用 LLM 分析机器人的失败，难点在于怎样把非结构化的多感官数据变成 LLM 能推理的文本。作者认为好的摘要要满足两点（§1）：
- **多感官**：有些失败靠声音更容易发现；
- **分层**：高层用来快速定位失败，低层保留解释所需的细节。

### 3. 方法

| 维度 | REFLECT |
| --- | --- |
| 存储来源 | 当前这一次执行的全部观测，执行结束后离线处理（§1、§3）。分三层：L0 是每一帧的任务相关场景图（物体、状态、空间关系、是否在夹爪里）和声音事件；L1 是事件关键帧的文字描述；L2 是每个子目标结束时的观测（§3.1）。 |
| 消费者 | 同一个 LLM（GPT-4，§5）在不同阶段扮演四个角色：子目标验证器读 L2；执行失败解释器读 L1；计划分析器读计划和最终状态；纠正规划器读解释、最终状态和目标（§3.2–3.3、附录 A.3）。同构。 |
| 定制依据 | 按分析阶段，由粗到细：先验证，失败了再调细节。场景图只保留计划里出现的物体，以及和它们有空间关系的物体（§3.1.1）。 |
| 压缩方式 | 规则式：场景图变化、声音事件起止、子目标结束，这三类条件触发关键帧（§3.1.2），关键帧再按模板转成文字。没有预算。 |
| 训练信号 | 不训练，零样本。仿真里物体检测和状态检测用真值，真机用 MDETR、CLIP、AudioCLIP（§5）。 |
| 更新与一致性 | 场景图跨帧聚合，用 ADD、UPDATE、REPLACE、DELETE 四条启发式规则，例如物体被操作后不再可见就删除（附录 A.2）。假设环境的其余部分保持静止（§5 Limitations）。 |
| 验证 | 核心就是验证：LLM 对每个子目标回答 Yes 或 No（§3.2、附录 A.3.1）。依据是从观测生成的摘要，不是规划器的信念；计划本身是给定的输入。 |
| 共享 vs 分开 | 没有直接对照。最接近的是“LLM summary”消融：先让 LLM 把 L0 压成一份通用摘要，再拿它做解释（§5）。 |
| 错误传播 | 没有研究。 |
| 成本 | 没有报告 token、延迟或调用次数。 |

## 四、HiMe

### 1. 基本信息

- arXiv 2607.03449v1；ICML 2026 poster。
- 作者单位：复旦（邱锡鹏）、上海创智学院、华东师大。
- 代码：[github.com/HappyWaterXP/HiMe](https://github.com/HappyWaterXP/HiMe)，核对的是 commit `261766e`。

### 2. 一句话和要解决的问题

**一句话**：把具身系统拆成三层：Executor（π₀.₅ VLA）只看当前观测和子任务；Sentry（小 VLM）看最近几帧，判断子任务完成没有；Planner（大 VLM）在 Sentry 触发时读写长期多模态记忆，并更新计划。

**问题**（§1）：
- VLA 只看当前观测，做不了依赖历史的任务；
- 用大模型管记忆又太慢，进不了实时控制环，作者称为“频率—能力悖论”；
- 只追加的记忆会积累过时、相互冲突的信息。

### 3. 方法

| 维度 | HiMe |
| --- | --- |
| 存储来源 | 当前任务的历史（一个任务里可能有多轮用户指令）：图像缓冲；Contextual Memory 记录，每条有标签、文本、至多一张代表图、更新时间；Procedural Memory，即计划表（§3.2；代码 `memory/multitag_recorder.py:16`）。 |
| 消费者 | 异构：Planner（GPT-4o，或 Qwen3-VL-30B）、Sentry（Qwen3-VL-8B）、Executor（微调后的 π₀.₅）（§3.4、附录 B）。 |
| 定制依据 | 人工固定分配（§3.3、Figure 2；代码见第 6 部分）：Planner 读指令、计划表、当前子任务内均匀采样的至多 8 帧，以及检索结果；Sentry 读计划表和最近 8 帧；Executor 读当前的两路图像、本体状态和子任务文本。 |
| 压缩方式 | Planner 通过增删改维护记忆，每条最多附一张代表图；给 Executor 的是子任务文本，是压缩得最狠的一种；Sentry 不压缩，只截取窗口。 |
| 训练信号 | 只有 Executor 用 60 条示范微调；Planner 和 Sentry 靠提示词（§3.4、附录 B）。 |
| 更新与一致性 | Planner 每次调用都做增删改；提示词要求状态变化时新建记录、把旧记录标为过去（附录 D）。没有来源追踪。 |
| 验证 | Sentry 判断 done 或 not_done，触发 Planner；Planner 再按自己的视图修改计划状态（§3.3）。Sentry 读的是 Planner 写的计划表，访问不了长期记忆。 |
| 共享 vs 分开 | 没有“所有模块拿同一份上下文”的对照。去掉 Sentry 的消融，同时改了触发方式和 Planner 的取帧方式（见第 6 部分）。 |
| 错误传播 | 没有测量。 |
| 成本 | 每个子任务的 Planner 调用次数（表 2）、Planner 端到端延迟（附录 C.4）；没有总 token。 |

### 4. 实验

- **平台和规模**：真机 WidowX-250，三个任务（Object Search、Counting、Rearrangement），每个方法每个任务 20 次（Figure 3、附录 A）。
- **基线**：都是自己实现的变体：Transient、Transient w/ Sentry、Flat Memory（作者说“类似 MemER”）、HiMe w/o Sentry，外加由人给子任务的 oracle（§4.2、表 1）。
- **指标**：Task Progress 是完成子任务的比例（附录表 5），不是整条任务的成功率。
- **关键数字**：
  - 主结果（Figure 4，三任务平均）：Transient 14，Transient w/ Sentry 26，Flat 65，HiMe w/o Sentry 68，HiMe 90，人给子任务的 oracle 94。
  - 管理方式消融（Figure 6）：FIFO 68，No management 86，HiMe 90。
  - 同容量 8 条（附录表 9，只在 Rearrangement 上做）：主动管理 80，FIFO 64，不限量 87。
  - Sentry 输入从 1 帧增加到 8 帧：精确率约 76% → 82%，召回约 22% → 35%（§5.4）。
  - Object Search 轮数从 1 增加到 3：记忆从 5.5 条增至 14.0 条，进度从 92.5% 降至 66.7%（附录表 10）。
  - Planner 中位延迟：GPT-4o 38.59s，Qwen3-VL-30B 6.83s（附录表 11）。
- **没做的**：方差或置信区间；和 MemER 等外部方法的真实对比；仿真基准（作者在 Limitations 里承认）。

### 5. 结论站不站得住

| 结论 | 证据强度 | 依据 |
| --- | --- | --- |
| 分层加记忆明显优于无记忆和 FIFO 平铺记忆 | 支持 | 90 vs 14／65（Figure 4），差距大、三个任务一致；但每格只有 20 次。 |

| 能根据人的偏好自我修正记忆 | 无 | 没有专门的指标或对照（摘要、§1）。 |

## 六、对我们方向的总体影响

**1. 面向验证的证据选择：有空间，但要小心。**
- REFLECT 已经在离线、单个 LLM 的设定下，用事件关键帧做逐子目标验证；RCR 的 Verifier 也拿到了按角色挑选的上下文。
- 所以“按事件给验证器挑证据”本身不能当新意，新意只能落在三点上：在线、限预算、和规划器的摘要相互独立。

**2. 错误连带：空间最大。**
- 四篇都没有测量；LatentMem 只在动机里提到。
- HiMe（Sentry 读 Planner 的计划表）和 RCR（所有角色从同一份由 agent 输出整理的记录里取）在结构上都天然存在连带，可以直接在它们的结构上做错误注入实验。

**3. 来源追踪与失效：中等。**
- REFLECT 和 HiMe 都有针对世界状态的增删改，RCR 有去重和“保留较新”的规则；但没有一篇处理“已经发给消费者的摘要”怎样失效。
- 【推断】离具体实验较远，适合作为第 1、2 条的支撑机制。

**4. 诊断矩阵：风险最低。**
- RCR 的 Figure 4 和 REFLECT 的消融是局部的先例，但都不是“删掉某类信息，看各消费者分别掉多少”的反事实矩阵。
- 【推断】适合作为第一步，也能顺带解释为什么 LatentMem、RCR 里“分开”的收益只有 1.3–6.45 个点。

**最危险的表述**有两种：“按消费者定制压缩”（LatentMem、RCR 已覆盖）和“为验证器挑选事件证据”（REFLECT 已覆盖）。

**【推断】建议**：
- 主线：共享摘要导致的错误连带，以及独立的验证视图能否切断它；
- 机制：在线、限预算的证据选择；
- 第一步：诊断矩阵；
- 基线：REFLECT 的事件规则、HiMe 的固定分配、RCR 式的按角色选择。
